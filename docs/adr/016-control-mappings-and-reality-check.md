# ADR-016: Control mappings (G7) and the reality check

Status: Proposed (M5.5 PR 1, chunk 1a); final when PR 1 closes. **Decision 2 is built in chunk 1b (commit to come); every other decision below is still planned** and is written so the owner can review it before any code exists. Facts about the Okta page were read on 2026-10-12 (by the owner's reviewer) and on 2026-10-13 (by the assistant, see decision 3).

## Context

M5 closed with two known gaps that M5.5 needs closed. First, `control_mappings` in a vault note's frontmatter are stored but cannot be searched (G7): the blast-radius preview and the reality check both need "which company policy documents map to this control". Second, ALIBI can say what a policy claims but cannot compare a claim with anything outside the vault. The product brief's promise is answers that are *backed*; a policy sentence "MFA is required" is not backed by an identity export that shows users without MFA.

PR 1 does both, offline and without a model: a scan-based `ControlMap` (G7), and a **reality check** that compares one policy claim with one offline IT export. The export is an Okta "MFA Enrollment by User" report CSV, the claim is "MFA required", and the result is a count of exceptions. The export is untrusted input that holds personal data (names, emails, phone numbers), and the check must never turn into a live connection to a customer system (a brief non-goal).

This ADR records the decisions so the owner can explain each one. It does **not** rewrite ADR-010 (line 48, "`control_mappings` search is deferred to M5") or ADR-013 (decision 7, "before G7 exists"). Both stay as accepted history; the threat-model backlog row G7 is the place that records the change.

## Decision

**1. Order of work (planned).** The docs-only sweep PR, then PR 1 to PR 4, each a separate branch off `main`, each merged with a merge commit. PR 1 (this one) is ControlMap plus the reality check; PR 2 is the promise ledger, run record, recall and blast radius (blast radius was folded in on 2026-10-13, deviation M55-3, to save a local CI pass; there is no PR 3); PR 4 is the contradiction detector. The edit-tool-only hook PR is deferred until API credits are replenished (deviation M55-2); ADR-015 stays reserved for it. The reasons, for the record: (a) deterministic features first, because PR 1 and PR 2 need no model and no live check, so they are fully testable offline; (b) the reality check is the only feature not blocked by the promise-creation design, which needed the owner's answers on the ledger, while this needed only the Okta format and the G7 approach; (c) the run record is the first change to shipped M5 code, so building the ledger second makes it likelier that change lands after GitHub Actions minutes return and CI can check it on `main`; (d) the model-dependent detector goes last, behind its own frozen evaluation and live check, so nothing else waits on that cycle.

**2. G7: a scan-based `ControlMap`, no schema change (built, chunk 1b).** A `ControlMap` reads the vault at call time (frontmatter `control_mappings` of each document, through the existing scanner and parser) and answers "which documents map to control X". It does not add an index table. Reasons: the index is disposable derived state (CLAUDE.md 8.1), a new table would change the schema and force a rebuild, and the vault is small enough to scan; a scan also cannot be stale. Identifiers are normalized with the existing `identifiers.py`. **The parent rule (the ADR-010 child rule):** looking up a parent control returns documents mapped to its enhancements (`IA-2` returns a document mapped to `IA-2(1)`), never the reverse. Matching is whole-identifier, never a substring (`AC-2` must not match `AC-20`). Mapping entries are usually written with a framework prefix (`NIST-800-53:IA-2`, `ISO27001:A.8.5`); the prefix is dropped before the identifier is recognized and is not checked against the rule that matched. **Caps, starting values chosen by the assistant (flagged, not measured), on top of the scanner's own file caps:** `MAX_DOCUMENTS = 2000`, where exceeding it is a **typed refusal** (`ControlMapTooLargeError`, code `control_map_too_large`), because a partial map would answer "no document maps to X" wrongly; and `MAX_MAPPING_ENTRIES = 64` per document, where exceeding it **leaves that document out of the map and reports it** (issue code `control_mappings_too_many`, counted in the report), so one hostile note cannot disable the lookup. An entry that is not a recognizable identifier is not mapped and is reported (`control_mapping_unrecognized`, counted). The document cap is applied after the scan, so it bounds the map, not the scanner's own work. Only NIST 800-53 enhancements have the parent relation. **Proof that retrieval is unchanged (done):** `git diff --stat` shows no file under `retrieval/` or `repositories/` changed, and `tests/test_retrieval_golden.py` passes unchanged. **What G7 closes:** the control-to-policy lookup. **What it does not close, now tracked as G31:** retrieval itself does not use `control_mappings` (no ranking boost, no filter). That belongs after M6, with the deferred M5m tuning, because changing retrieval would move the evaluation numbers.

**3. The one supported format: Okta "MFA Enrollment by User" (planned).** Page: `https://help.okta.com/oie/en-us/content/topics/reports/mfa-enrollment-user-report.htm`. Read on **2026-10-12** by the owner's reviewer and on **2026-10-13** by the assistant with a fetch tool that summarizes pages with a small model (the same limit as threat-model Section 8), and the two lists were compared. The 13 CSV headers, which differ from the Admin Console labels: `user.id`, `user.fullName`, `user.email`, `user.mobilePhone`, `authenticators.type`, `authenticators.count`, `groups.name`, `user.isAdmin`, `user.status`, `user.login`, `user.primaryPhone`, `user.created`, `user.activated`. All 13 matched in name and number. From the page: `authenticators.type` is a comma-separated list of the distinct types a user has enrolled (and can include the Forgotten Password Question for migrated Classic Engine orgs); `authenticators.count` counts distinct *types*; email authenticators are included "even when the email authenticator isn't enabled for authentication"; `user.status` values are "such as Active, Pending user action, Deprovisioned, Suspended, or Staged". **The page does not document the type strings Okta writes.** No real export has been seen; fixtures and tests will use example strings, labeled as examples, and never any employer's data.

**4. Four columns are read (planned).** `user.login` (to name exceptions), `user.status`, `authenticators.type`, `user.isAdmin`. If one of the four headers is missing the reader refuses with a typed `missing_column` naming the header. The other nine are not kept (decision 11 states the honest limit).

**5. MFA is decided from a list, never from a count (planned).** The `authenticators.type` cell is split on commas, each part stripped, and intersected with an owner-confirmed set. A user is "with MFA" if the intersection is non-empty; an empty cell means no MFA. `authenticators.count` is never used: it counts distinct types and so counts password and email, which are not MFA. Because the strings are undocumented, `POST /reality/inspect` first returns the distinct values found after splitting, with counts, and the owner confirms the set before any count.

**6. The default MFA set is the owner's policy decision (planned).** The default is Okta Verify, security keys, and phone (SMS or voice). Email and password never count. **Plain note: SMS and voice codes can be phished, intercepted or SIM-swapped, so counting phone as MFA is a policy choice, not a statement that phone is strong.** The set **should match the policy being checked**, and the owner confirms it at the inspect step. The demo confirms the set **without phone**, because `vault-demo/vault/access-control-policy.md:23` says "Text-message codes are not an accepted second factor"; under that set a phone-only user is an exception. The request carries two lists chosen from the inspect values, `mfa_types` (the confirmed set) and `phone_types` (the values the owner identifies as phone; may be empty). The result adds a **phone-only** count. An in-scope user is phone-only when they have **at least one type in `phone_types`** and **no type in `mfa_types` that is not also in `phone_types`**. It is computed whether or not phone is in the confirmed set. **A user with no MFA-capable type at all is not phone-only** (they are simply without MFA), so an empty intersection can never count as phone-only. With `phone_types` empty the count is 0, and the result says no phone types were named. **A confirmed type that is absent from the file is reported (`mfa_types_not_present`, names only) and never refused**, so the default set works on a file that lacks some of its types, such as an export with no security-key users.

**7. Scope, and the admin count (planned).** `user.status` equal to `Active` is in scope (the owner can confirm the set). Every other status is counted and reported as skipped with its status text, never dropped silently. Among in-scope users without MFA, the result counts those with `user.isAdmin` true; a value that is not true or false (case-insensitive) is counted as `admin_unknown`.

**8. A streaming reader, and an honest retention rule (planned, chunk 1d).** CLAUDE.md 8.4 reads a whole workbook once, hashes it and parses the same bytes. For an export that would hold every name, email and phone number in one object, and the standard `csv.reader` hands each row's columns over as strings regardless. So the reader reads the file inside a new approved root (`GRC_IMPORT_DIR`, through `resolve_within`) **once, in 64 KiB chunks, hashing the bytes incrementally and decoding incrementally**, so the hash is of exactly the bytes parsed. It keeps the four fields of each row and drops the rest at once. **The honest rule: nothing outside the four fields is kept past its row, stored, logged or returned.** No parser can avoid seeing a row's other columns for an instant, and this ADR does not claim otherwise. Cells are read as text only; a cell that begins with `=`, `+`, `-` or `@` is data and is never evaluated. Nothing is written to a file. A later export of results to a spreadsheet must pass `sanitize.py` (a backlog precondition).

**9. Caps and encodings, starting values (planned; flagged, not yet measured).** 10 MiB per file, 100,000 rows, 4,096 characters per field, 200 listed exceptions (the rest only counted). Encodings: UTF-8, UTF-8 with BOM, and UTF-16 with BOM as spreadsheet tools write them; anything else is a typed refusal; NUL bytes are refused. A duplicate required header is refused. Duplicate `user.login` values are reported as a count. These are starting values chosen by the assistant; any change to a cap that a test needs is a stop-and-ask.

**10. The claim finder is code, not the model (planned, chunk 1e).** It scans company-policy chunks of the vault (read-only) for sentences that contain an MFA term (`MFA`, `multi-factor`, `multifactor`, `two-factor`, `2FA`, matched case-insensitively) and a requirement term (`must`, `shall`, `required`, `require`). The lists were checked against the demo's rule, `vault-demo/vault/access-control-policy.md:23`, which begins "Multi-factor authentication (MFA) is required for all staff accounts" and so matches on both lists. **A hard test is planned for chunk 1e: that sentence is found.** When several match, all are listed and none is chosen silently; the owner picks one by path and lines, and the quote is re-verified verbatim at check time. A sentence with an exception or scope word is shown, not interpreted (the demo's rule names "staff accounts" while an Okta export covers every user). `ControlMap` is used to rank and cross-check, never to hide: a claim in a document not mapped to an authentication control is listed with a note saying so. The claim is shown beside the counts. Reason for no model: a model would add a way for the result to be wrong or to be steered by vault text, and the sentence match is simple enough to read and test.

**11. "Never compliant" wording (planned).** The result states "this export, this claim, this date; not evidence the control works". The finding is `exceptions_found` or `no_exceptions_in_export`, never "compliant". The date is the owner's `exported_at` input, shown with the file's SHA-256; staleness is the owner's responsibility and the result says so.

**12. No live connection, and how that is enforced (planned).** There is no URL, token, credential or host parameter in any request model. The `reality/` module imports no network or process module (a test, like the demo-workbook tool's), `csv` may be imported only under `reality/` (a Semgrep rule with fixtures), and the egress guard stays on for the whole suite. The reality check has no model and needs no live check.

**13. The authentication-controls file (planned, chunk 1c).** `sidecar/src/grc_sidecar/reality/auth_controls.json` lists the control IDs treated as authentication controls (used by `ControlMap` to rank and cross-check claims). The owner reviews the list at STOP R1. Candidates, checked against the shipped packs on 2026-10-13: NIST SP 800-53 Rev 5 `IA-2`, `IA-2(1)`, `IA-2(2)` (headings, `packs/nist-sp800-53-r5/ia.md:22`, `:28`, `:34`); NIST SP 800-171 Rev 3 `03.05.03` (heading, `packs/nist-sp800-171-r3/03.05.md:21`); NIST CSF 2.0 `PR.AA-03` (heading, `packs/nist-csf-2.0/pr.md:28`); SOC 2 `CC6.1` (bold list item, `packs/soc2-tsc-ids/cc.md:28`); ISO 27001 `A.8.5` (bold list item, `packs/iso27001-annex-a-ids/a8-technological.md:15`). A test requires every ID in the file to exist in the shipped packs. **The owner's decision of 2026-10-13: the test accepts a heading or a bold list-item ID (`- **ID**`).** For the SOC 2 and ISO packs, which are authored and whose `id_list_verified_against` is `unverified` (F11-2), this proves the ID is present in **our authored pack**, not that it is in the standard.

**14. The administrators' hardware-key requirement is a later claim (planned).** The demo sentence at `access-control-policy.md:23` also says administrators must use a hardware security key. v1 checks only "MFA required"; that second claim is not checked, and the result does not imply it is.

**15. Logging (planned).** CLAUDE.md Section 7 allows content at DEBUG; the first-party code goes further and writes none (the F13-1b practice). The reality check logs no export content at any level, **including identifiers such as `user.login`**. Counts, codes and exception type names are allowed. A canary test plants a canary in `user.login` and in a dropped column and shows it in no log record at INFO and at DEBUG.

## Consequences

- G7 closes for the control-to-policy lookup (threat-model row updated when PR 1 closes); G31 opens for retrieval, so the gap is named and owned, not hidden.
- The reality check gives a deterministic, offline, testable answer to "does the export contradict the claim", and its limits are in its wording: one format, one claim, undocumented type strings, an owner-confirmed MFA set. Residual risks that stay open: the default set counts SMS, and the type strings are unverified against a real export (recorded in the new threat-model rows F25-9 and F25-10, labelled "No mitigation, accepted", and they stay accepted when PR 1 closes; the other new rows F25 and F26 are "No mitigation (planned, M5.5 PR 1)" until chunks 1b to 1e land).
- A new approved root, `GRC_IMPORT_DIR`, joins the others; its overlap rules and the route behavior when it is unset (503 `import_root_not_configured`) are built in chunk 1d.
- The `auth_controls.json` data file must be packaged with the sidecar (an M8 item).
- ADR-010 and ADR-013 keep their text; a reader finds the current state of G7 in the threat-model backlog and here.
- **Mutation proofs:** chunk 1b is below. Rows for chunks 1c to 1e are added as they land, in the ADR-014 style (control broken with the edit tool, named test fails, file restored byte for byte, hashes shown).
