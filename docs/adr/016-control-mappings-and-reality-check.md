# ADR-016: Control mappings (G7) and the reality check

Status: Proposed (M5.5 PR 1, chunk 1a); final when PR 1 closes. **Built so far:** decision 2 in chunk 1b (commit cf23d95); decision 13 in chunk 1c (commit b38705e); decisions 4, 8, 9 and 15 (for the reader), the inspect half of decision 5, and the enforcement of decision 12 (the `csv` Semgrep rule, the import-folder overlap rule and the no-network test) in chunk 1d (commit 1ddba52); and, in chunk 1e (commit to come), the claim finder and `POST /reality/check`: decisions 5 (counting half), 6, 7, 10, 11 and the check and claims parts of 15. **Every other decision below is still planned** and is written so the owner can review it before any code exists. Facts about the Okta page were read on 2026-10-12 (by the owner's reviewer) and on 2026-10-13 (by the assistant, see decision 3).

## Context

M5 closed with two known gaps that M5.5 needs closed. First, `control_mappings` in a vault note's frontmatter are stored but cannot be searched (G7): the blast-radius preview and the reality check both need "which company policy documents map to this control". Second, ALIBI can say what a policy claims but cannot compare a claim with anything outside the vault. The product brief's promise is answers that are *backed*; a policy sentence "MFA is required" is not backed by an identity export that shows users without MFA.

PR 1 does both, offline and without a model: a scan-based `ControlMap` (G7), and a **reality check** that compares one policy claim with one offline IT export. The export is an Okta "MFA Enrollment by User" report CSV, the claim is "MFA required", and the result is a count of exceptions. The export is untrusted input that holds personal data (names, emails, phone numbers), and the check must never turn into a live connection to a customer system (a brief non-goal).

This ADR records the decisions so the owner can explain each one. It does **not** rewrite ADR-010 (line 48, "`control_mappings` search is deferred to M5") or ADR-013 (decision 7, "before G7 exists"). Both stay as accepted history; the threat-model backlog row G7 is the place that records the change.

## Decision

**1. Order of work (planned).** The docs-only sweep PR, then PR 1 to PR 4, each a separate branch off `main`, each merged with a merge commit. PR 1 (this one) is ControlMap plus the reality check; PR 2 is the promise ledger, run record, recall and blast radius (blast radius was folded in on 2026-10-13, deviation M55-3, to save a local CI pass; there is no PR 3); PR 4 is the contradiction detector. The edit-tool-only hook PR is deferred until API credits are replenished (deviation M55-2); ADR-015 stays reserved for it. The reasons, for the record: (a) deterministic features first, because PR 1 and PR 2 need no model and no live check, so they are fully testable offline; (b) the reality check is the only feature not blocked by the promise-creation design, which needed the owner's answers on the ledger, while this needed only the Okta format and the G7 approach; (c) the run record is the first change to shipped M5 code, so building the ledger second makes it likelier that change lands after GitHub Actions minutes return and CI can check it on `main`; (d) the model-dependent detector goes last, behind its own frozen evaluation and live check, so nothing else waits on that cycle.

**2. G7: a scan-based `ControlMap`, no schema change (built, chunk 1b).** A `ControlMap` reads the vault at call time (frontmatter `control_mappings` of each document, through the existing scanner and parser) and answers "which documents map to control X". It does not add an index table. Reasons: the index is disposable derived state (CLAUDE.md 8.1), a new table would change the schema and force a rebuild, and the vault is small enough to scan; a scan also cannot be stale. Identifiers are normalized with the existing `identifiers.py`. **The parent rule (the ADR-010 child rule):** looking up a parent control returns documents mapped to its enhancements (`IA-2` returns a document mapped to `IA-2(1)`), never the reverse. Matching is whole-identifier, never a substring (`AC-2` must not match `AC-20`). Mapping entries are usually written with a framework prefix (`NIST-800-53:IA-2`, `ISO27001:A.8.5`); the prefix is dropped before the identifier is recognized and is not checked against the rule that matched. **Caps, starting values chosen by the assistant (flagged, not measured), on top of the scanner's own file caps:** `MAX_DOCUMENTS = 2000`, where exceeding it is a **typed refusal** (`ControlMapTooLargeError`, code `control_map_too_large`), because a partial map would answer "no document maps to X" wrongly; and `MAX_MAPPING_ENTRIES = 64` per document, where exceeding it **leaves that document out of the map and reports it** (issue code `control_mappings_too_many`, counted in the report), so one hostile note cannot disable the lookup. An entry that is not a recognizable identifier is not mapped and is reported (`control_mapping_unrecognized`, counted). The document cap is applied after the scan, so it bounds the map, not the scanner's own work. Only NIST 800-53 enhancements have the parent relation. **Proof that retrieval is unchanged (done):** `git diff --stat` shows no file under `retrieval/` or `repositories/` changed, and `tests/test_retrieval_golden.py` passes unchanged. **What G7 closes:** the control-to-policy lookup. **What it does not close, now tracked as G31:** retrieval itself does not use `control_mappings` (no ranking boost, no filter). That belongs after M6, with the deferred M5m tuning, because changing retrieval would move the evaluation numbers.

**3. The one supported format: Okta "MFA Enrollment by User" (planned).** Page: `https://help.okta.com/oie/en-us/content/topics/reports/mfa-enrollment-user-report.htm`. Read on **2026-10-12** by the owner's reviewer and on **2026-10-13** by the assistant with a fetch tool that summarizes pages with a small model (the same limit as threat-model Section 8), and the two lists were compared. The 13 CSV headers, which differ from the Admin Console labels: `user.id`, `user.fullName`, `user.email`, `user.mobilePhone`, `authenticators.type`, `authenticators.count`, `groups.name`, `user.isAdmin`, `user.status`, `user.login`, `user.primaryPhone`, `user.created`, `user.activated`. All 13 matched in name and number. From the page: `authenticators.type` is a comma-separated list of the distinct types a user has enrolled (and can include the Forgotten Password Question for migrated Classic Engine orgs); `authenticators.count` counts distinct *types*; email authenticators are included "even when the email authenticator isn't enabled for authentication"; `user.status` values are "such as Active, Pending user action, Deprovisioned, Suspended, or Staged". **The page does not document the type strings Okta writes.** No real export has been seen; fixtures and tests will use example strings, labeled as examples, and never any employer's data.

**4. Four columns are read (built, chunk 1d).** `user.login` (to name exceptions), `user.status`, `authenticators.type`, `user.isAdmin`. Each must appear exactly once in the header: a missing one is a typed `missing_column` and a repeated one a typed `duplicate_column`, each naming the header (one of our four constant names, never text from the file). The other nine are not kept (decision 8 states the honest limit). **A data row whose cell count differs from the header is never reshaped** (no padding of a short row, no trimming of a long one, no guess at a row shifted by an unquoted comma): it is counted as `malformed_rows`, yields no record and is excluded from every other count. Chunk 1e will skip such rows from the check and report the count. A malformed row still counts toward the row cap, so a hostile file cannot dodge it. (Owner change at the chunk 1d plan review, 2026-10-13.)

**5. MFA is decided from a list, never from a count (built: the inspect half in chunk 1d, the counting half in chunk 1e, `reality/check.py`).** The `authenticators.type` cell is split on commas, each part stripped, and intersected with an owner-confirmed set. A user is "with MFA" if the intersection is non-empty; an empty cell means no MFA. `authenticators.count` is never used: it counts distinct types and so counts password and email, which are not MFA. Because the strings are undocumented, `POST /reality/inspect` first returns the distinct values found after splitting, with counts, and the owner confirms the set before any count. **Built in chunk 1d:** `POST /reality/inspect` returns the file's SHA-256 and size, the count of well-formed data rows, the count of malformed rows, the rows per `user.status` value, the distinct authenticator types after splitting on commas and stripping (with counts, each user counted once per type), and the count of duplicate `user.login` values. It returns no login, name, email or phone; duplicate logins are found by remembering a hash of each login, never the login. Status and type strings are untrusted file text, so each is shortened to 64 characters for display (with a `truncated` flag) and at most 200 distinct values are listed per kind (the rest only counted); both numbers are starting values chosen by the assistant, flagged for review.

**6. The default MFA set is the owner's policy decision (built, chunk 1e: the request carries `mfa_types` and `phone_types`; the check applies exactly the set it is given and the default set is the caller's to send).** The default is Okta Verify, security keys, and phone (SMS or voice). Email and password never count. **Plain note: SMS and voice codes can be phished, intercepted or SIM-swapped, so counting phone as MFA is a policy choice, not a statement that phone is strong.** The set **should match the policy being checked**, and the owner confirms it at the inspect step. The demo confirms the set **without phone**, because `vault-demo/vault/access-control-policy.md:23` says "Text-message codes are not an accepted second factor"; under that set a phone-only user is an exception. The request carries two lists chosen from the inspect values, `mfa_types` (the confirmed set) and `phone_types` (the values the owner identifies as phone; may be empty). The result adds a **phone-only** count. An in-scope user is phone-only when they have **at least one type in `phone_types`** and **no type in `mfa_types` that is not also in `phone_types`**. It is computed whether or not phone is in the confirmed set. **A user with no MFA-capable type at all is not phone-only** (they are simply without MFA), so an empty intersection can never count as phone-only. With `phone_types` empty the count is 0, and the result says no phone types were named. **A confirmed type that is absent from the file is reported (`mfa_types_not_present`, names only) and never refused**, so the default set works on a file that lacks some of its types, such as an export with no security-key users.

**7. Scope, and the admin count (built, chunk 1e; details after the original text).** `user.status` equal to `Active` is in scope (the owner can confirm the set). Every other status is counted and reported as skipped with its status text, never dropped silently. Among in-scope users without MFA, the result counts those with `user.isAdmin` true; a value that is not true or false (case-insensitive) is counted as `admin_unknown`. **As built:** the request carries `active_statuses` (default `["Active"]`); a status is in scope when its stripped text is exactly one of them (letter case matters). The admin value is compared after stripping spaces and ignoring case. **Duplicate logins:** every well-formed row is counted on its own and nothing is merged, because the reader cannot know which row is "the" account; `duplicate_logins` counts the repeats (by hashing, never by keeping a login), and the result carries a fixed note that a duplicated login can be an exception on one row and not on another. The exception list is per row, in file order, with `user.login` stripped and shown to 256 characters (a `truncated` flag), at most 200 listed and the rest counted (`exceptions_not_listed`); it is in the authenticated response only. **A check with nobody in scope is refused** (`no_users_in_scope`, HTTP 422): "no exceptions" about nobody would be a false assurance, and inspect shows the status values. `mfa_types_not_present` is computed over every well-formed row of the file, any status. The `authenticators.count` column is not just unused: the reader never keeps it, so no code path could use it.

**8. A streaming reader, and an honest retention rule (built, chunk 1d: `reality/export_reader.py`).** CLAUDE.md 8.4 reads a whole workbook once, hashes it and parses the same bytes. For an export that would hold every name, email and phone number in one object, and the standard `csv.reader` hands each row's columns over as strings regardless. So the reader reads the file inside a new approved root (`GRC_IMPORT_DIR`, through `resolve_within`) **once, in 64 KiB chunks, hashing the bytes incrementally and decoding incrementally**, so the hash is of exactly the bytes parsed. It keeps the four fields of each row and drops the rest at once. **The honest rule: nothing outside the four fields is kept past its row, stored, logged or returned.** No parser can avoid seeing a row's other columns for an instant, and this ADR does not claim otherwise. Cells are read as text only; a cell that begins with `=`, `+`, `-` or `@` is data and is never evaluated. Nothing is written to a file. A later export of results to a spreadsheet must pass `sanitize.py` (a backlog precondition). **How it is built:** the file is opened once, after `resolve_within`; the reader yields one record at a time and never builds a list of rows; the record keeps four fields and its `repr` shows none of them. Decoded text is split **only on `"\n"`** (never `str.splitlines`, which also splits on U+2028, U+2029, `\x0b`, `\x0c`, `\x1c` to `\x1e` and `\x85` and would cut a quoted field in two); the csv module reads `"\r\n"` and newlines inside quotes, including across a 64 KiB chunk boundary. Failures from the decoder and the csv module become a fixed refusal code after their `except` block, so no chained exception can quote file bytes. `csv.field_size_limit` is never changed (it is process-wide); the reader checks every cell's length itself, the nine dropped columns included.

**9. Caps and encodings, starting values (built, chunk 1d; flagged, not yet measured).** 10 MiB per file, 100,000 rows, 4,096 characters per field, 200 listed exceptions (the rest only counted). Encodings: UTF-8, UTF-8 with BOM, and UTF-16 with BOM as spreadsheet tools write them; anything else is a typed refusal; NUL bytes are refused. A duplicate required header is refused. Duplicate `user.login` values are reported as a count. These are starting values chosen by the assistant; any change to a cap that a test needs is a stop-and-ask. **Refusal codes (chunk 1d), all fixed words, HTTP 422 `export_refused`:** `file_too_large`, `too_many_rows`, `field_too_long`, `encoding_not_allowed`, `nul_character`, `missing_column`, `duplicate_column`, `unreadable` (not a regular file, or an OS error). UTF-32 marks and UTF-16 without a mark are refused; a cut-off multibyte sequence at the end is refused. The 200 listed exceptions belong to the check (chunk 1e), not to inspect.

**10. The claim finder is code, not the model (built, chunk 1e: `reality/claims.py`, `GET /reality/claims`).** It scans company-policy chunks of the vault (read-only) for sentences that contain an MFA term (`MFA`, `multi-factor`, `multifactor`, `two-factor`, `2FA`, matched case-insensitively) and a requirement term (`must`, `shall`, `required`, `require`). The lists were checked against the demo's rule, `vault-demo/vault/access-control-policy.md:23`, which begins "Multi-factor authentication (MFA) is required for all staff accounts" and so matches on both lists. **A hard test (built): that sentence is found, at line 23, mapped to an authentication control; the next sentence, about the administrators' hardware key, is not a candidate.** When several match, all are listed and none is chosen silently; the owner picks one by path and lines, and the claim is re-verified at check time. **Built, with two owner changes at the chunk 1e plan review (2026-10-13):** (a) the submitted claim (path, start line, end line, quote) must EQUAL a candidate the finder produces from the current vault, the quote compared as a whole after `grounding.normalize` on both sides (whitespace runs collapsed, nothing else folded); a fragment of a candidate, such as the sentence with its qualifier words cut off, is refused `claim_not_verbatim`. (b) The claim's document is looked up only among the documents `scan_vault` returns, so the scanner's path guard and symlink refusal apply and the requested path is never opened; an outside path or a link matches no candidate. The quote is the sentence with whitespace collapsed; list markers and `>` marks are removed, fenced code and the frontmatter are not searched; a heading or a table row is one unit. Sentences are cut after `.`, `!` or `?` followed by whitespace, except after "e.g.", "i.e." and "vs."; an unusual abbreviation can still cut a sentence short, so the owner reads the quote. `qualifier_words` (a fixed display list of exception and scope words) is shown beside each candidate and changes no count. Starting values chosen by the assistant, flagged and unmeasured: a sentence over 1,000 characters is counted (`too_long`) and not listed; at most 100 candidates are listed (the rest counted); the request's quote is capped at 2,000 characters. The finder scans the vault once and `ControlMap` scans it once more (two read-only scans); `GET /reality/claims` takes no parameters, so GET, and a vault with too many documents for the control map is a typed 422 `control_map_too_large`. A sentence with an exception or scope word is shown, not interpreted (the demo's rule names "staff accounts" while an Okta export covers every user). `ControlMap` is used to rank and cross-check, never to hide: a claim in a document not mapped to an authentication control is listed with a note saying so. The claim is shown beside the counts. Reason for no model: a model would add a way for the result to be wrong or to be steered by vault text, and the sentence match is simple enough to read and test.

**11. "Never compliant" wording (built, chunk 1e).** The result states "this export, this claim, this date; not evidence the control works". The finding is `exceptions_found` or `no_exceptions_in_export`, never "compliant". The date is the owner's `exported_at` input, shown with the file's SHA-256; staleness is the owner's responsibility and the result says so.

**12. No live connection, and how that is enforced (enforcement built in chunk 1d).** There is no URL, token, credential or host parameter in any request model (`tests/test_reality_hygiene.py` checks that the only field of the inspect request is `file`). The `reality/` module imports no network or process module (an AST test that also sees `__import__` and `importlib`), `csv` may be imported only under `reality/` (Semgrep rule `grc-py-csv-outside-reality`, with `ruleid:` and `ok:` fixtures that include `import os, csv` and `import csv, os`, plus an AST test as the second layer), and the egress guard stays on for the whole suite. The reality check has no model and needs no live check.

**13. The authentication-controls file (built, chunk 1c).** The file holds exactly these seven IDs, each with its framework, pack folder and pack file, and is read by `reality/auth_controls.py` with `importlib.resources` (strict Pydantic, every ID recognized by `identify`, duplicates and malformed files refused with `AuthControlsError`). `tests/test_auth_controls.py` proves each ID is a heading or a `- **ID**` item in its cited pack file. `sidecar/src/grc_sidecar/reality/auth_controls.json` lists the control IDs treated as authentication controls (used by `ControlMap` to rank and cross-check claims). The owner reviews the list at STOP R1. Candidates, checked against the shipped packs on 2026-10-13: NIST SP 800-53 Rev 5 `IA-2`, `IA-2(1)`, `IA-2(2)` (headings, `packs/nist-sp800-53-r5/ia.md:22`, `:28`, `:34`); NIST SP 800-171 Rev 3 `03.05.03` (heading, `packs/nist-sp800-171-r3/03.05.md:21`); NIST CSF 2.0 `PR.AA-03` (heading, `packs/nist-csf-2.0/pr.md:28`); SOC 2 `CC6.1` (bold list item, `packs/soc2-tsc-ids/cc.md:28`); ISO 27001 `A.8.5` (bold list item, `packs/iso27001-annex-a-ids/a8-technological.md:15`). A test requires every ID in the file to exist in the shipped packs. **The owner's decision of 2026-10-13: the test accepts a heading or a bold list-item ID (`- **ID**`).** For the SOC 2 and ISO packs, which are authored and whose `id_list_verified_against` is `unverified` (F11-2), this proves the ID is present in **our authored pack**, not that it is in the standard.

**14. The administrators' hardware-key requirement is a later claim (planned).** The demo sentence at `access-control-policy.md:23` also says administrators must use a hardware security key. v1 checks only "MFA required"; that second claim is not checked, and the result does not imply it is.

**15. Logging (built for the reader and inspect in chunk 1d, and for the claims and check routes in chunk 1e).** CLAUDE.md Section 7 allows content at DEBUG; the first-party code goes further and writes none (the F13-1b practice). The reality check logs no export content at any level, **including identifiers such as `user.login`**. Counts, codes and exception type names are allowed. A canary test plants a canary in `user.login` and in dropped columns and shows it in no log record at INFO and at DEBUG, nor in the inspect answer, a refusal or a record's repr (`tests/test_reality_routes.py`). The only log line the reader path writes is a count line (`rows`, `malformed`, `duplicates`).

## Consequences

- G7 closes for the control-to-policy lookup (threat-model row updated when PR 1 closes); G31 opens for retrieval, so the gap is named and owned, not hidden.
- The reality check gives a deterministic, offline, testable answer to "does the export contradict the claim", and its limits are in its wording: one format, one claim, undocumented type strings, an owner-confirmed MFA set. Residual risks that stay open: the default set counts SMS, and the type strings are unverified against a real export (recorded in the new threat-model rows F25-9 and F25-10, labelled "No mitigation, accepted", and they stay accepted when PR 1 closes; the other new rows F25 and F26 are "No mitigation (planned, M5.5 PR 1)" until chunks 1b to 1e land).
- A new approved root, `GRC_IMPORT_DIR`, joins the others (built in chunk 1d). It may not equal, sit inside or contain the vault, the index, the questionnaire folder or the export folder: checked lexically when settings load and again on the resolved paths in `validate_runtime_dirs`. When it or `GRC_VAULT_DIR` is unset, the reality routes answer 503 `import_root_not_configured`. The host's five-key child environment is unchanged (the host does not pass the new variable until M6).
- The `auth_controls.json` data file must be packaged with the sidecar (an M8 item).
- ADR-010 and ADR-013 keep their text; a reader finds the current state of G7 in the threat-model backlog and here.
- **Mutation proofs:** chunk 1b is below. Rows for chunks 1c to 1e are added as they land, in the ADR-014 style (control broken with the edit tool, named test fails, file restored byte for byte, hashes shown).
