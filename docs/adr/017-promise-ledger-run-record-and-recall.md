# ADR-017: Promise ledger, run record and recall

Status: Proposed (M5.5 PR 2); final when PR 2 closes. **Chunk 2b (the store) is built; the rest is not.** Decisions 6, 7, 8, 10 (normalization), 14 and 20 (storage side) are marked *(built in chunk 2b)*; every other decision is marked *(planned)* and names the chunk that builds it: 2b the store, 2c the run record, 2d the import and the offline draft tool, 2e recall. The design is from the approved M5.5 plan (revision 2b, with deviations M55-1 to M55-4). It is written before any M5 file is touched so the owner can review it at STOP L1. Facts about the code were read on 2026-10-13.

## Context

M5 writes answers into a draft workbook that every cell marks `[UNREVIEWED DRAFT]`. Nothing records what happens next: a person reviews the draft, sends some answers to a customer, and later edits the policy those answers rest on. The answer already sent is now a **promise** the company made, and nobody is told when the policy behind it changes. The product brief's word is *backed*: an answer should stay linked to the exact policy lines it came from, and the owner should find out when those lines move.

PR 2 adds three things, all offline and none using a model: a **ledger** of promises the owner chose to record (append-only, local), a **run record** that lets the ledger know what ALIBI itself wrote into a draft, and **recall**, an on-demand re-check of each promise against the current vault. The model is never asked whether a promise is still true; code compares lines and hashes and says what changed. The blast-radius preview (what an edit to a policy would break) reuses recall's pure check; it gets its own ADR-018 in a later chunk of this PR.

This ADR records the decisions so the owner can explain each one. It **amends ADR-014 decision 16 by addition** (decision 15 below) and does not change ADR-014's text. It also relies on, and does not change, ADR-014 decisions 10 (the writer is the only module that saves a workbook) and 11 (what is stored in a cell is cleaned by `sanitize.py`).

**Every number marked "starting value" below is unmeasured.** None was measured on real data; they are the assistant's choices, flagged for the owner's review, as M5 did.

## Decision

**1. Promise creation is Option A, tightened (built in chunk 2d).** A promise is created by importing a **reviewed draft workbook**: the owner opens the draft ALIBI wrote, types `approved` in the `Review` column of the answers they accept, sends them, and then tells ALIBI which customer received them and when. **Option C** (typing a promise in by hand) stays a later extension. **Option B** (mark a whole run as sent) is **rejected**: no human reads the text before it becomes a promise, which is exactly the failure the product exists to prevent. The first approval path in ALIBI is therefore a human act on a file, never a model output (decision 14 of ADR-013 keeps review state apart from evidence status; this adds the first way for the review field to be anything but `unreviewed`).

**2. The workbook supplies two things; the run record supplies everything else (built in chunks 2c and 2d).** From the reviewed workbook the import reads only the `Review` mark and the final Answer cell text. Status, reasons, the citation (vault-relative path, lines, quote), the model name and digests, and every baseline hash come from **ALIBI's own run record** (decision 15). The Evidence cell is **compared** with a hash of what ALIBI wrote; it is never parsed. A hand-edited Evidence cell cannot invent a citation, because no citation is read from the workbook. The request carries the full hex `run_id` (so a renamed workbook still joins its run), a `file` name inside the export folder (through `resolve_within`; the owner saves the reviewed copy in place with **Save**, not Save As), the customer choice (decision 10) and `sent_on` (decision 11). The workbook is read with the existing loader (`read_input_bytes`, `load_questionnaire`: byte scan, caps, same bytes parsed); the import code never saves it, and the existing rule that `.save(` appears only in `writer.py` still holds. The sheet, header row and first new column come from the run record; the six ALIBI header titles must be found where the record says, else the import is refused (`headers_changed`).

**3. The exact hash definitions (built in chunk 2c; every hash is sha256 over UTF-8).**
- `question_sha256`: the question text after the engine's own whitespace normalization (`grounding.normalize`: runs of whitespace become one space, ends trimmed). The text is `QuestionRow.text` as extracted (`questionnaire/mapping.py`).
- `answer_cell_sha256`, `status_cell_sha256`, `evidence_cell_sha256`: the string **exactly as stored in the cell**, meaning the value `_put_text` returns after `clean_cell_text` (`questionnaire/writer.py:144-156`). The Answer is taken after `remove_direction_controls` (`writer.py:130`); the Status is `result.status`; the Evidence is `_evidence_text` (`writer.py:107-119`), including the direction marker when present. **Each is taken from the final result, after the changed-source lowering (`_lowered`, `writer.py:277-282`, applied at `writer.py:325`), not from the result the model produced.** NULL when no cell was written. Hashing after `sanitize.py` is what lets an unedited row never read as edited, including text that `clean_cell_text` changed (control characters, line endings, the length cap).
- `cited_lines_sha256`: the cited lines of the file as the indexer sees it (`decode_and_normalize`, then `split_lines`, lines `start_line..end_line` joined with `\n`, the same rule as `Chunk.text`, `vault/models.py`).
- `cited_file_sha256`: the `Citation.file_sha256` the answer carried (the hash of the normalized file as indexed). By the end of a run the writer has already compared it with the file's current hash for every cited file (`lower_for_changed_source`).
- `row_sha256`: over each row's own fields, to detect **accidental** corruption only. It is not a signature and no tamper evidence is claimed (decision 9).

**4. The review vocabulary (built in chunk 2d), one definition.** Take the `Review` cell text; strip **ASCII spaces and tabs only** from both ends; if the result contains any non-ASCII character, or any internal whitespace (extra words), it is **not recognized** and is listed under "other values". Otherwise compare case-insensitively (ASCII). `approved` is approved (so `Approved `, `APPROVED` and a trailing tab are accepted; a test will **expect** acceptance of a trailing space). `rejected` and `unreviewed` are recognized and **counted separately, not stored**. Anything else is "other". Each "other" value is reported with its exact text, shortened to 64 characters with a truncation flag, and its count, in the authenticated response only, never in a log. A homoglyph, a non-breaking space or a zero-width character makes a value "other", so it is never approved.

**5. Per-row skip codes and whole-import refusals (built in chunk 2d).** Every skip has a reason code and a count; none is silent.

| Code | When |
|---|---|
| `not_approved` | Review is not `approved` (decision 4 says how it is counted) |
| `no_answer` | the run record says the row was blank or `NEEDS_REVIEW`, **or** the Answer cell is blank; includes a blank or `NEEDS_REVIEW` row the owner filled in by hand, which has no verified source and so cannot be recalled |
| `status_edited` | the Status cell text differs from the hash of what ALIBI wrote |
| `evidence_edited` | the Evidence cell text differs from the hash of what ALIBI wrote (a blank Evidence cell where one was written counts as edited) |
| `baseline_unavailable` | the run record holds no cited-lines hash for that answer (the cited file could not be read at the end of the run, or its hash differed from the one the answer carried) |
| `already_imported` | a promise already exists for this customer, run and **row** (re-import is safe) |

**Whole-import refusals:** every question row the run record knows is read from the workbook at the same row number and hashed. **If any hash differs, or the workbook has fewer or more question rows than the record, the whole import is refused** (`question_mismatch`: sorted or deleted rows, or a different workbook), with a count of mismatched rows and never text. Also refused: unknown `run_id`; no run record (`run_record_missing`: a run without a record cannot produce promises); `headers_changed`; a file outside the folder; the loader's own refusals (the same codes as `inspect`).

**6. Uniqueness is customer, run and row; the question hash is not the key (built in chunk 2b).** `UNIQUE(customer_id, run_id, run_row_index)`. A questionnaire can repeat a question, so two identical questions have equal hashes at different rows and **both must import**. If the question hash were the key, the second would be skipped as `already_imported`. The question hash is kept as data and does one job: it is the check that rows were not moved (decision 5). A test will import a run with two identical questions, and a mutation proof will key uniqueness on the hash and require that test to fail.

**7. Storage is its own folder, `GRC_LEDGER_DIR`, and not the index (built in chunk 2b).** The file is `<GRC_LEDGER_DIR>/ledger.sqlite3`. There is **no default**: unset gives a typed 503 `ledger_root_not_configured`, and a questionnaire run still works (decision 15). The index is "disposable derived state" (CLAUDE.md 8.1) and can be rebuilt at any time; a ledger cannot be rebuilt from anything. Wiping or rebuilding the index must never delete promises, so the ledger is not stored in or beside it. One new setting, `ledger_dir`, is added; `import_dir` already exists (built in M5.5 PR 1, ADR-016). `ledger_dir` is absolute, declared after the existing folders (the overlap validators read earlier fields), and **may not equal, sit inside or contain** the vault, the index, the questionnaire folder, the export folder or the import folder, in both directions (no other folder may sit inside or contain it either), checked lexically when settings load and again on resolved paths in `validate_runtime_dirs`. The host's five-key child environment is unchanged until M6. Storage is stdlib `sqlite3` through the existing `SqliteWorker` (one worker thread owns the connection) behind a typed `LedgerRepository` protocol in `repositories/`, so the repository pattern holds and the store is swappable. No new dependency.

**8. Append-only is enforced twice (built in chunk 2b).** (1) The repository exposes no update or delete method. (2) SQLite `BEFORE UPDATE` and `BEFORE DELETE` triggers on **every** table `RAISE(ABORT)`. Tests will remove the trigger and separately bypass the repository, and mutation proofs will remove each trigger and add an update method. **Honest limit:** a same-user process can open the file and drop the triggers (O1).

**9. What "Immutable" in ALIBI means, stated plainly (planned wording for the product).** The product name says *Answers Linked to Immutable, Backed Information*. In this PR "immutable" means **immutable to the application**: there is no code path that updates or deletes a ledger row, the repository and the triggers enforce that, and mutation proofs will show the controls matter. It does **not** mean tamper-evident. A same-user process can edit the SQLite file, and `row_sha256` is only for accidental corruption. **Answer receipts** (a signed or chained record that would let someone detect tampering) **remain the planned feature** for that, and are not built here. The ledger stores hashes and claims no tamper evidence.

**10. Customers (normalization and the unique key built in chunk 2b; the import request built in chunk 2d).** The import request carries either `{"existing_customer_id": ...}` or `{"new_customer_name": ..., "confirm_new": true}`. A new name without `confirm_new` is refused. A name that normalizes to an existing customer is refused with that customer's id (`customer_exists`). One customer per import. Normalization: Unicode NFC, trim, collapse whitespace, casefold; the display name is kept as typed, at most 200 characters, control characters refused. The customer table's unique key is the normalized name.

**11. The sent date is the owner's, and bounded (built in chunk 2d).** `sent_on` is an ISO date supplied by the owner. It is refused if after `Clock.today()` (`sent_on_in_future`) or before the run record's `created_on` (`sent_before_drafted`). ALIBI does not send anything and cannot know when a customer received an answer, so it records the owner's statement and checks only that it is possible.

**12. The baseline is the policy as it was when drafted (planned, chunk 2d).** A promise's baseline (`cited_lines_sha256`, `cited_file_sha256`) comes from the run record, not from the vault at import time. Import does **not** re-verify the quote against the current vault and does not refuse because the policy changed after drafting. It calls the same pure `check_promise` (decision 17) once per created promise on the current vault and reports a count `already_changed_since_draft` as information, so the owner sees at import that a promise starts life flagged. The earlier idea of an `imported_without_run_record` origin is removed: no run record, no promise.

**13. Corrections are `voided` events; the owner's "I saw it" is `acknowledged` (planned, chunks 2b and 2e).** A promise is never edited or deleted. A `voided` event carries a reason code from a fixed set (`wrong_customer`, `imported_in_error`, `not_actually_sent`, `other`), no free text, so it opens no new content channel. Voided promises are excluded from recall and from listings by default (`include_voided` shows them; history is kept). `acknowledged` records that the owner saw a flag.

**14. Dates come from `Clock.today()`; event ids are integers (built in chunk 2b).** `sent_on`, `created_on` and an event's `on_date` are dates, from the injected `Clock` (the only place the sidecar reads the system date, `vault/clock.py`; a hygiene test already enforces that). `promise_event.event_id` is `INTEGER PRIMARY KEY AUTOINCREMENT`, so the order of events does not depend on a timestamp, and `Clock` gains no method. A date, not a time, is enough for what the ledger must say ("sent on", "last checked on") and avoids a second clock the tests would have to control.

**15. The run record, and the amendment by addition of ADR-014 decision 16 (built in chunk 2c).** This is the first change to shipped M5 code, so it has its own review (STOP L2). Facts: `QuestionnaireRuns._execute` (`questionnaire/runs.py:250-301`) answers all questions, calls `write_answers`, then builds a `RunSummary` with counts only; `write_answers` computes each row's final (possibly lowered) result and the stored cell strings **inside** the function, and the `ExportResult` it returns holds none of them (`writer.py:68-78`). So the change is additive: (a) `ExportResult` gains one defaulted field carrying, per question row, the final status and reasons, the citation, and the three stored cell strings or their hashes, computed where `stored` is already known; existing callers keep working because the field has a default; the strings never go into `RunSummary`, events or logs. (b) `RunDependencies` (`runs.py:81-96`) gains an optional `run_recorder` (a small Protocol); `None` means "no ledger". (c) After the file is written, the cited lines' hash is computed with one read per cited file through a new public function in `vault/scan.py` that shares the scanner's file-safety and read-limit helpers with `current_file_sha256`, returning the file hash and the cited lines' hash from the same bytes, **and, when the file cannot be read, the reason (`not_found`, `unsafe_path`, `too_large` or `not_utf8`) instead of a bare `None`**, which recall (decision 17) turns into the `missing` detail code; if that file hash differs from `Citation.file_sha256`, the baseline is NULL (`baseline_unavailable` at import). (d) **Ledger folder unset:** the run works exactly as today and the summary warnings gain `run_record_not_kept`. **Record write fails:** the run still completes, the warning is `run_record_failed`, and a fixed code is logged, never exception text. (e) **Order:** the record is written after the output file, so a record always belongs to a file that exists. A crash between the two leaves a draft with no record, which cannot produce promises.

*What this amends in ADR-014, by addition only.* Decision 16 says runs are held in memory (the last 20 finished runs, gone after a restart) and that events and routes carry codes, never text. **That stays true.** What decision 16 does not say, and this decision adds, is that when `GRC_LEDGER_DIR` is configured, a **separate durable run record** is also written to the ledger at the end of each run, holding hashes and a quote but no answer text; the in-memory run state, the events and the summary are unchanged apart from the two new warning codes. ADR-014 itself is not edited. Decisions 10 and 11 are relied on as written: the recorder does not save a workbook (the writer stays the only saver), and the cell hashes are taken after `sanitize.py`.

**16. The offline draft tool, and what it does and does not prove (planned, chunk 2d).** A reviewer cannot test the Excel round trip without a draft that has a run record and real `SUPPORTED` or `PARTIAL` rows, and ALIBI never runs a live model for this. So `sidecar/tests/offline_draft.py`, run from `sidecar/` as `python -m tests.offline_draft <draft|import-check>`, builds one. It lives with the test kits because it reuses them (`FakeModel` and `cite(...)`, `FakeGate`, `FakeModelReader`, the retrieval `stack(...)`); a module under `tests/` with a `main` is new for this repo, and `tools/`, which cannot import `tests/` cleanly, is worse. `draft` takes the four folders the owner names, refuses folders that overlap (it builds a `Settings`, so the same overlap rules apply), copies `vault-demo/vault` into a work folder (the frozen original is only read), builds the index there with the real indexer and a fake embedder, writes the demo workbook with exclusive create, and runs the **real** `QuestionnaireRuns` with the real loader, answer service, retriever, `write_answers` and the **real run recorder**. Only the model (scripted, quoting phrases chosen from the copy), the gate, the digest reader and the embedder are fake; every phrase still goes through the real status check, so it prints each row's **actual** status and reason codes (never text), the run id and the draft's file name. `import-check` calls the **same import service the route calls** and prints counts, each created promise's `edited_after_draft`, and the refusal code if any. **Safety:** it never builds a `GenerationClient` or any `httpx` client and never touches port 11434 (a test asserts the module imports neither, and a run under the socket guard shows no connect); it writes only into the folders named, by exclusive create; its output holds no document, question or answer text. **What it proves:** the Excel round trip and the hashes (an Excel-saved copy of an unedited draft imports with every row `edited_after_draft` false and no `question_mismatch`; STOP L3 is the owner running exactly that). **What it does not prove:** anything about a real model's answers, and the HTTP route and its authentication (the route has its own tests). If the manual check fails, the failure is reported and the hashing is not adjusted quietly.

**17. Recall: states, flags and the three fixes (planned, chunk 2e).** Recall is a pure function `check_promise(promise, current_text | None, today) -> RecallResult`, shared with blast radius. The states are `intact`, `moved`, `changed` and `missing`. Rules: (1) no text (file missing, a symlink or junction, outside the root, too big, not UTF-8): `missing`, **carrying a detail code that says why**: `not_found`, `unsafe_path` (a symlink, a junction or a path outside the root), `too_large` or `not_utf8`. A bare "missing" would make the owner guess whether the file was deleted or merely unreadable. (2) The cited lines' sha256 equals `cited_lines_sha256`: `intact`. (3) Otherwise find every place the stored quote occurs (whitespace-normalized verbatim, the `grounding.normalize` rule and nothing else, in a new function in `questionnaire/grounding.py` built on `normalize_with_map`): at other lines only, `moved`; at the same lines but with changed text, or nowhere, `changed` (detail code `cited_lines_changed` or `quote_not_found`). Independently, the current frontmatter `review_by` before `Clock.today()` adds the information flag `review_overdue`; an unparseable frontmatter adds `frontmatter_invalid` and says the review date is unknown. **The three fixes**, each a mutation proof: **(a)** if the cited lines' text changed, the result is **never `intact`**, even when the quote still sits at the same lines (a changed sentence around a quote must be flagged); **(b)** `moved` carries **every** location the quote occurs at, not the first; **(c)** `document_changed_elsewhere` is an information flag, not a state: when the cited lines are intact but the whole file's hash differs from `cited_file_sha256`, the result stays `intact` and says the rest of the document changed. **Every recall result carries a fixed statement, in these words: "intact means the cited lines are unchanged since drafting; it does not mean the promise is still true."** It is part of the result, not of the documentation, so no reader of a recall report can take `intact` for a verdict. A mutation proof will remove the statement from a result and require a test to fail. Recall is on demand only, `POST /ledger/recall` (a POST because it can append events), bounded (a cap on promises per call, starting value 2,000, unmeasured), reads each distinct vault file once, and never calls a model.

**18. Recall watches the cited lines only (planned, chunk 2e).** A promise rests on specific lines, and `intact` says only that they are unchanged since drafting (the fixed statement of decision 17). A change elsewhere in the same document does not change what was promised, so it is not a state change; it only adds `document_changed_elsewhere` (decision 17c). The consequence is stated plainly: if a *different* paragraph is edited so that it now contradicts the cited lines, recall says `intact`. Finding contradictions between policy statements is the separate PR 4 detector, not recall. Likewise, code cannot tell whether an edited answer still matches its quote (`edited_after_draft` records only that the text differs from what ALIBI wrote; the limit is the same as F12-2c).

**19. Recall reads the vault, not the index (planned, chunk 2e).** The index is derived state and can be stale; a promise check that read it could report `intact` for lines that changed on disk. Recall reads the current vault file through the shared read function in `vault/scan.py` (one read; the text is hashed once and parsed from the same text), so what is checked is what is on disk now. A mutation proof will make recall read the index and require a test to fail. Blast radius supplies proposed text to the same function instead of a vault read.

**20. Events, not updates (storage side built in chunk 2b; the recall side is planned, chunk 2e).** A promise row never changes. What changes is a new `promise_event` row (`created`, `recall_state_changed`, `acknowledged`, `voided`); the current state is the latest recall event. Recall appends an event only when a promise's state differs from its last event, so repeated checks do not grow the ledger. This is what makes append-only (decision 8) workable: history is kept, and nothing needs an edit.

**21. Items for the M8 setup guide (planned, M8).** The ledger cannot be rebuilt, so the guide must say: back up `GRC_LEDGER_DIR`; never put it in a sync folder (a sync client can lock, duplicate or conflict-copy a SQLite file); copy it only while ALIBI is closed (a copy during a write can be torn). These are the owner's decision on the plan's Q5; the guide itself is M8 work.

## Consequences

Positive (once built): a promise keeps the exact lines it rested on, as they were when drafted, and the owner can ask at any time which promises those lines no longer back; the import refuses a different workbook, sorted rows or an edited Status or Evidence cell rather than guessing; nothing about this needs a model, so it can be fully tested offline and a result never depends on a model's mood; the product's "Immutable" is stated at exactly the strength the code can enforce.

Negative or risky:

- **Not tamper-evident (O1).** A same-user process can alter the ledger file. Answer receipts are the planned remedy and are not built.
- **Plaintext at rest.** Customer names, questions, answers and quotes are stored unencrypted; the O4 disk-encryption assumption applies, and the threat model gets a row for it (Section 7).
- **The `Review` mark is a file edit.** Anyone who can edit the workbook can type `approved`. The product treats it as the owner's act; a forged workbook from a same-user process is O1.
- **Hashing depends on how Excel saves text.** Line endings or trimming could differ after an Excel save. STOP L3 is the only way to see it; if it fails, the report says so and the hashing is not changed quietly.
- **Recall is blind outside the cited lines** (decision 18) and cannot judge whether an edited answer still matches its quote.
- **Starting values are unmeasured:** 2,000 promises per recall call; import rows bounded by the existing 500-question cap; listing page size 100. They may be wrong; a refusal because of one is reported, not worked around.
- **Changes shipped M5 code.** The run record (decision 15) touches `writer.py` and `runs.py`; the existing M5 tests run unchanged at STOP L2, and the change is additive (a defaulted field, an optional recorder).
- **Planned threat-model rows** F27 to F31 (`docs/threat-model.md`, Sections 5 to 7) are all **No mitigation** today, planned or accepted, and change label only when the chunk that builds each control lands with a resolvable test.
- **Not in this ADR:** blast radius (ADR-018), the contradiction detector (ADR-019), a ledger export to a spreadsheet (would need `sanitize.py` and an F23-class review, backlog item G32), sending anything to a customer, and the M6 approval screen.

### Chunk 2b: details the build settled

These are choices made while building the store, for the owner's review: (1) a customer's display name is stored **exactly as typed** (not trimmed), at most 200 characters, and is refused if it holds a control (`Cc`), format (`Cf`, which covers zero-width and direction-override characters) or surrogate (`Cs`) character, or is empty once normalized; `Cf` is refused because a zero-width character would let two visually identical names be two customers. (2) The `promise_event` row hash leaves out `event_id`, which SQLite assigns at insert. (3) A row whose hash no longer matches is a typed `LedgerStoreError` on read (fail closed), not a silent bad value. (4) `add_promise` writes the promise and its `created` event in one transaction, so a promise never exists without its first event; callers cannot append `created` themselves. (5) A `voided` event is refused unless its `detail_code` is one of the four fixed reasons, and `recall_state_changed` is refused without a state. (6) Foreign keys are on. (7) The ledger file is never inspected for repair: a version mismatch, a non-ledger SQLite file or a non-database file is `LedgerSchemaMismatchError` and the file is left byte-identical.

### Chunk 2c: details the build settled

The run record (decisions 3 and 15) is built. These are choices made while building it, for the owner's review: (1) `ExportResult` gains one defaulted field, `rows`, a tuple of `ExportedRow` (row, question hash, final status and reasons, final citation, and the three cell hashes). Hashes, not cell text, are kept, and nothing of it reaches `RunSummary`, events or logs. (2) `vault/scan.py` gains `read_cited_file(vault_root, source_path, ranges)`, which takes a **list** of line ranges rather than one, so a file cited by several answers is still read exactly once (a test counts the reads). It returns the file hash and one lines hash per range, or one of the reasons `not_found`, `unsafe_path`, `too_large`, `not_utf8`. An unreadable file and a missing vault root are `not_found`; a link, a path outside the root and the resolved-path mismatch are `unsafe_path`. A range that does not lie inside the file has no hash (None). (3) `_safe_file` is now a thin wrapper over a new `_locate_file` that says why it refused; `current_file_sha256` and the scanner behave exactly as before (their tests are unchanged, and a new test pins `current_file_sha256` returning None for each refusal). (4) `RunDependencies` gains `run_recorder` (None means no ledger) and `read_cited`, whose default reads nothing, so a baseline is NULL and never wrong when it is not wired. (5) When Ollama gave no digest (for example the second read at the end of a run failed), the record stores the fixed word `unavailable`, because `NewRunRecord` requires a string and the 2b schema is not changed; the alternative was to lose the record. (6) The recorder wrapper `LedgerRunRecorder` opens the ledger file on the first record, so a configured but unused ledger creates no file; the ledger repository is closed with the runtime. (7) `create_app(..., ledger=)` and `app.state.ledger` exist for the chunk 2d routes; nothing reads them yet. (8) Warning codes: `run_record_not_kept` (no ledger folder) and `run_record_failed` (any failure while recording, including the vault read and the ledger; the log line holds the fixed code and the exception's type name, never its message). (9) Ledger folder unset or a record that fails changes nothing else: the summary is equal apart from `warnings` (a test compares two runs).

### Chunk 2d: details the build settled

The reviewed-workbook import (decisions 1, 2, 4, 5, 10 and 11) is built as `ledger/review.py` (the vocabulary), `ledger/reviewed.py` (reading the workbook against the record), `ledger/service.py` (the import and the listings) and `api/ledger.py` (`POST /ledger/import`, `GET /ledger/customers`, `GET /ledger/promises`). These are choices made while building it, for the owner's review:

1. **Order.** A missing export folder (`export_root_not_configured`, 503) is answered before anything is read from the ledger, because a configuration problem should not look like a data problem. Then: `run_record_missing`, the path guard and the loader, `headers_changed`, `question_mismatch`, the customer, the sent date, then the per-row rules. Every refusal happens before anything is written.
2. **`extract_questions` gained one defaulted keyword,** `reading_a_draft` (shipped M5 code, additive). A draft always carries ALIBI's answer columns, so only the `already_has_answer_columns` refusal is skipped; everything else is the code that read the questions when the run started, so the rows mean the same thing. Its default is unchanged and no existing test changed.
3. **`question_mismatch` counts three things in one number:** a recorded row whose question hash differs, a recorded row the workbook no longer has, and a question row the workbook has that the record does not. The response carries `mismatched_rows`, `workbook_rows` and `recorded_rows` and never text. The sheet, header row and question column come from the record; the id column is not recorded and does not affect any hash.
4. **A new customer is created only when at least one promise will be created,** after every refusal check, because the ledger is append-only and a refused or empty import must leave nothing behind. The name is still validated first (a public `validate_customer_name` was added to the repository module, a two-line wrapper over its existing private check), so a bad name is refused even when nothing would be created. Promises are written one transaction each, so an import that is interrupted can be run again: the finished rows are skipped as `already_imported`, and a repeat with the same new name is refused as `customer_exists` with the id to use.
5. **The review vocabulary is decision 4 exactly, with two gaps filled:** a blank Review cell counts as `unreviewed` (the text the writer puts there itself, so a cleared cell means no decision), and a Review cell that is not text (a number, a date, a boolean) is `other`. "Other" values are grouped by their shortened text and flag, reported in the authenticated response only, and never logged.
6. **An Answer cell that is not text is never converted to text.** Only the cell types text (`s`) and typed formula (`f`, kept as its text and never evaluated) count as an answer. A number, a date, a boolean or an error value such as `#N/A` (which the reader returns as a string but marks as an error) makes the row `no_answer`, counted. A blank or whitespace-only Answer cell is `no_answer` too. An Answer the owner typed into a row ALIBI left blank is `no_answer` as well: it has no verified source.
7. **What a promise keeps.** The citation, both baseline hashes and the status come from the run record; the question text is the hash-verified workbook row as typed; the answer text is the Answer cell exactly as the owner left it; `edited_after_draft` is true when its sha256 differs from the recorded hash. The import does not re-check the quote against the current vault.
8. **The routes need the ledger, and only the import needs the export folder.** With no ledger folder every route answers `ledger_root_not_configured`. With a ledger folder but no export folder (so no questionnaire runtime) the import answers `export_root_not_configured`, and the two listings keep working. One repository serves the whole process: the service wraps the questionnaire runtime's repository when there is one, and builds and closes its own otherwise. `LedgerStoreError` now maps to `503 ledger_store_error` (it had no mapping).
9. **Limits.** A page is 100 promises (a starting value, unmeasured). A promise is voided when any of its events is `voided`; finding that costs one query per promise, which is fine at one owner's scale and would need a repository method if the ledger grew. The routes take a name of at most 1,000 characters as a bound on the request; the ledger's own name rules decide the rest.
10. **Not built yet:** `already_changed_since_draft` (decision 12) needs recall's `check_promise` and waits for chunk 2e. The threat-model rows F29 and F30 are not relabelled in this chunk; the tests named in the table below are what they will cite.
