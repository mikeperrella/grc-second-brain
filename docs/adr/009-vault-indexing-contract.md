# ADR-009: Vault indexing contract

Status: Proposed. M3a fixes the parsing, normalization, chunking, link and path rules below, which are implemented and tested. M3b implements the store half of the sections marked "M3b" (concurrency, schema versioning, and the repository's side of the stale-evidence invariant). The parts that need the indexer and the embedding client (marked "Draft: M3c") are completed, and the status changed, when that chunk lands.

## Context

The Markdown vault is the single source of truth (CLAUDE.md 8.1). Everything the indexer stores is derived and disposable, and every answer must cite a verifiable file and line range. Vault files are untrusted input (CLAUDE.md 8.6). So the rules for reading a file have to be exact, identical on Windows and Linux, and hostile-input safe.

## Decision (implemented in M3a)

**Text normalization** (`vault/normalize.py`). UTF-8 only; a leading BOM is dropped; invalid UTF-8 or a NUL byte is an error (no latin-1 fallback, which would silently produce wrong text). CRLF and lone CR become LF. Lines are split on `\n` only, never `str.splitlines()`, which also splits on U+2028, U+0085, `\x0b` and `\x0c` and would make our line numbers disagree with an editor's. No Unicode normalization: exact quotes must match the source. Files over 2 MiB are rejected without being read in full.

**File hash.** `file_sha256` is the SHA-256 of the *normalized* text, not of the raw bytes, so the same content has the same ID on Windows (CRLF) and Linux (LF). This is our reading of "sha256(file)" in CLAUDE.md 8.1. Future answer receipts hash the normalized text too, for the same reason.

**Frontmatter** (`vault/frontmatter.py`). `doc_id`, `type`, `owner` are required. `review_by` is required unless `type` is `framework` or `note` (generated framework text has no review cycle, and a placeholder date would be a lie). `control_mappings` and `links` are optional lists. Unknown keys are ignored and reported as info notes. `review_by` must be exactly `YYYY-MM-DD` and a real calendar date.

YAML is read by `StrictFrontmatterLoader`, a `SafeLoader` subclass, instantiated directly (`yaml.load` is banned by Semgrep rule `grc-py-yaml-unsafe-load` and a hygiene test). It guesses no types: dates, `yes`/`no`/`NO`, `007` and `1e3` all stay text, and Pydantic checks each field against its real type. Aliases, anchors, explicit tags and duplicate keys are rejected, and the block is capped at 64 KiB. The loader owns a *copy* of PyYAML's resolver table; editing the inherited table would silently change `yaml.safe_load` for every other caller in the process, so a test proves it is unchanged. An unquoted `links: [[x]]` (or the same in `control_mappings`) is read by YAML as a list inside a list, so it gets its own error code, `FRONTMATTER_UNQUOTED_WIKILINK`, telling the user to quote it.

**Chunking** (`vault/chunker.py`, `vault/markdown.py`). A chunk is a contiguous run of lines. Line numbers are 1-based, inclusive and counted in the original file, so frontmatter lines count even though they are not chunked. Sections split at ATX headings outside code fences; a section over 2000 characters splits at blank lines; a fenced code block is never split unless it alone exceeds the embedding limit; a heading is never a chunk by itself (it joins what follows). `chunk_id` = SHA-256 of a canonical JSON encoding of `(source_path, doc_id, file_sha256, start_line, end_line)`, exactly the CLAUDE.md 8.1 contract, with `source_path` vault-relative and forward-slashed. Each chunk also stores `text_sha256`, the hash of its own text; the ID contract is unchanged. Limits: setext headings and indented code blocks are not recognized. The embedded string (prefix + heading path + text) is capped at `HARD_MAX_EMBED_CHARS`, provisionally 6000, to be measured against the real model in M3c and *lowered* (never by raising the model's context) if it fails; one line longer than the cap keeps its full stored text and only its embedding input is cut, and the chunk is flagged.

**Links** (`vault/links.py`). Forms: `[[t]]`, `[[t|alias]]`, `[[t#heading]]`, `[[t#^block]]`, `![[t]]`, and frontmatter `links`. Links inside code fences and inline code are ignored. Resolution uses only the in-memory set of already-validated documents (by vault-relative path, then `doc_id`, then unique file name); it never touches the filesystem, so a link cannot cause a read outside the vault. Targets that look like they leave the vault (absolute or drive paths, UNC, backslashes, `..` segments, URL-like text, NUL) are `rejected`. A target that matches nothing is `unresolved`, one that matches several documents is `ambiguous`. Nothing is guessed.

**Scanning and path safety** (`vault/scan.py`). The vault root comes only from typed configuration (`GRC_VAULT_DIR`). No IPC command or HTTP route takes a path yet, so the Rust-side `canonicalize` + `starts_with` check from CLAUDE.md 3.6 stays deferred to the chunk that adds the folder picker, which owns adding it. Every file goes through the shared `resolve_within` guard, and the resolved path must also equal the plain "root + relative path" that was walked, so any symlink or Windows junction is refused, even one pointing inside the vault. Symlinked folders are not entered. Only `*.md` files are read; any path component starting with `.` (`.obsidian`, `.git`, hidden files) is skipped silently. There is no README exception: a vault's documentation belongs outside its root, as in `vault-sample/README.md`. Known gap: creating a junction needs a subprocess, so junction handling is covered by the equality rule but has no test.

**Failure policy.** One bad file never stops a scan. Each problem becomes an `IndexIssue` naming the vault-relative path, field and line, with a code, and never any document text or input value. Errors keep fixed messages (the existing convention); path, field and line are attributes. The bad file is excluded, so it is never served. If two files declare the same `doc_id`, *all* of them are excluded, because "first one wins" would depend on directory order.

## Decision (store: implemented in M3b; indexer: Draft, M3c)

**Stale evidence invariant (store half implemented in M3b; the indexer's half is Draft, M3c).** `begin_sync` and `replace_document` implement the transactions described below; `Indexer.sync` and `refresh_staleness()`, and the tests that drive a crash and a reopen through them, arrive in M3c. `replace_document` also deletes every row the document already has before inserting, inside its own transaction, so it is correct even when a caller never ran `begin_sync` (`test_replace_document_twice_without_begin_sync_leaves_no_old_rows`); that makes the "no old row survives a replace" rule a property of the repository, not of the order in which the indexer calls it. Deleting a source's chunks must never lag behind the file (CLAUDE.md 8.1; the OWASP RAG Security Cheat Sheet makes the same two points: deletion must propagate to the vector store and derived indexes, and a document whose hash no longer matches what was ingested should be excluded from retrieval, failing closed). A sync first scans, then in one transaction deletes every document that is gone or malformed and, for every changed document, deletes its chunk, vector, full-text and link rows and sets `documents.stale = 1` (the `documents` row is kept so integrity checks can report it). Only after that does it embed. `replace_document` inserts the new rows and clears `stale` in one transaction. Because stale documents have no rows, no read path needs a stale filter, and a nearest-neighbour search that returns its top k rows before any filter cannot be starved by hidden stale rows. *Invariant:* for any scan whose first transaction committed, after `sync` returns, raises, or the process dies at any later point, every document whose stored hash differs from the file's hash at scan time has `stale = 1` and no rows in any searchable table. The guarantee is relative to the latest committed scan; an edit made after it cannot be seen by any index, so `refresh_staleness()` (scan plus that first transaction, no embedding) exists for M4 to call before answering.

**Concurrency (M3b, implemented).** `Indexer.sync` is `async def` and tests call it with `asyncio.run`; library code never calls `asyncio.run`, so M4 can call it from FastAPI handlers. Every `VectorRepository` method is `async`. One dedicated thread (`SqliteWorker`, a `ThreadPoolExecutor` with one worker, named `grc-index-db`) owns the SQLite connection: the connection is created on that thread and `check_same_thread` is left on, so a call from any other thread raises `sqlite3.ProgrammingError` instead of corrupting state (`test_the_connection_cannot_be_used_from_another_thread`), and every repository method dispatches to the worker. One worker also serializes all writes, so there is no lock logic. If a task is cancelled mid-transaction, the thread still finishes the call and the transaction commits or rolls back whole; nothing is left half applied. A thread is not a process, so the ADR-007 guard is unaffected. No `pytest-asyncio` is used. **Errors (M3b).** Only domain errors cross the boundary. In `_run`, a `GrcError` is re-raised as it is (`ExtensionLoadBlockedError` is also a `PermissionError`, so it must not be remapped); `sqlite3.Error`, `OSError` and pydantic's `ValidationError` become `IndexStoreError` with a fixed message, because they can quote SQL, a path, or (the pydantic one) the value of the bad column, which is document text. The plain `ValueError` for an out-of-range `k` is not mapped. The domain error is raised **after** the `except` block, by setting a flag inside it. `raise ... from None` is not enough: it only hides the original from the traceback printout, and the original, with its message, stays attached as `__context__`. The tests assert `__cause__` and `__context__` are both `None` and that a sentinel string (`CONFIDENTIAL POLICY TEXT`) is absent from the message. The same pattern is used in `_inspect`, `_connect` and `rebuild_index`. `_delete_rows` raises if no transaction is open, so a delete cannot commit by itself.

**Schema versioning (M3b, implemented).** The schema version is `PRAGMA user_version` (`SCHEMA_VERSION`, currently 2). Version 2 made `chunks.rowid` `INTEGER PRIMARY KEY AUTOINCREMENT`, so a rowid is never handed out twice. The reason: `vec_chunks` and `fts_chunks` share `chunks.rowid`, so with reuse a leftover vector or FTS row left behind by a bug would be silently adopted by the next chunk that received that rowid (a wrong vector, or stale text) and `verify_integrity()` could not see it, because it would no longer be an orphan. `test_a_deleted_chunks_rowid_is_never_reused` and `test_a_leftover_vector_row_stays_visible_as_an_orphan_after_new_chunks` pin it. `meta` holds the embedding profile (`embedding_model`, `embedding_model_digest`, `embedding_dim`, `doc_prefix`, `query_prefix`). `open_or_create` first opens an existing file **read-only** to read the version and `meta`, so the old file is never written to. The index is disposable, so a version mismatch means rebuild, never migrate: with `auto_rebuild=True` (the default) the old file is deleted and a fresh index created; with `auto_rebuild=False` `IndexRebuildRequiredError` is raised and the file is left byte-identical. A file that is not a SQLite database at all, or whose `meta` is damaged, always raises `IndexRebuildRequiredError` and is never deleted automatically (it may not be ours), so a human decides, using `rebuild_index(index_dir, file_name)`, which deletes one `*.sqlite3` file (and a leftover `-journal`) inside the index folder and nothing else. An **embedding profile mismatch** (model, digest, dimension or prefixes) raises `IndexProfileMismatchError`, naming only the fields, and writes nothing, because re-embedding everything is the user's decision. A `chunker_version` mismatch is not an error: `begin_sync` marks every document as changed and the indexer re-indexes it. Deviation from the M3 plan, small: `chunker_version` is stored per document (`documents.chunker_version`) and not also in `meta`, because it is compared per document and has no whole-index meaning. This does not apply to the future M5.5 promise ledger, which is durable user data in a separate database file and will need real migrations.

**Where the index lives (M3b).** `Settings.index_dir` (`GRC_INDEX_DIR`, absolute) must not be inside `vault_dir` (rejected when settings load, and again for the default). Unset means `~/.grc-second-brain/index`, which `resolve_index_dir()` works out when the index is opened and **not at startup**: the host starts the sidecar with an allowlisted environment that has `GRC_LOG_DIR` but no home directory, so a home-based default evaluated at startup would make the shipped sidecar exit 2 over a setting nothing uses yet (the same reasoning as the CLAUDE.md 3.7 deviation below). The host sets `GRC_INDEX_DIR` when M4 wires the index in. **Note for M4 (no code in M3):** the Rust host builds the sidecar's environment from an allowlist (`child_env.rs`, M2a), which today passes exactly `SYSTEMROOT`, `GRC_AUTH_TOKEN` and `GRC_LOG_DIR`, and has a test that forbids `HOME`, `USERPROFILE` and other inherited variables. When M4 wires the index in, that allowlist must add `GRC_INDEX_DIR` and `GRC_VAULT_DIR` (absolute paths, from host configuration), or the sidecar will never see them and will fall back to the defaults (no vault, and the home-based index folder, which does not exist in that environment). The file is `vault-<first 16 hex of sha256(canonical vault root)>.sqlite3`, so two vaults never share an index.

**Deviation from CLAUDE.md 3.7.** That rule says the sidecar checks at startup that the required Ollama models exist. M3 provides the check (`GET /api/tags` before every indexing run, failing closed, never `/api/pull`) but does not wire it into sidecar startup, because refusing to start when Ollama is down would change the M2 host flows. It is wired in M4 together with the app-level dependency wiring.

## Consequences

- The same file gives the same chunk IDs on every platform, and a frontmatter-only edit changes every ID of that file (as CLAUDE.md 8.1 requires), so the file is re-embedded.
- Recall (M5.5) keys on `(doc_id, text_sha256)`, not on a path or line range, so a rename or an edit elsewhere in the file is distinguishable from an edit to the cited passage.
- Strict YAML rejects some frontmatter that Obsidian itself would tolerate (unquoted wikilinks). The error says exactly how to fix it.
- Rejecting every symlink is stricter than necessary for a vault that symlinks inside itself, and is easy to relax later with a decision of its own.
