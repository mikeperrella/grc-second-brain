# ADR-022: M6.5 screens, ledger writes from the window, and the approval scope

Status: **Proposed (M6.5 chunk 65a); nothing in it is built.** Written 2026-10-18 from `M6_5_PLAN.md`. No screen, route change, test or control described here exists yet. Every screen is for a **debug build only until M8**: release builds cannot start the sidecar until then, and there is no installer. The wording of every fixed statement named here is a **draft for the owner's approval**. All caps, sizes and counts are unmeasured starting values. If this ADR disagrees with CLAUDE.md, the accepted ADRs or the threat model, they win.

## Context

M6 core gave the window folders, a vault index action, a questionnaire run and a read-only review queue (ADR-020, ADR-021). The ledger, recall, blast radius, contradiction detector and reality check have sidecar routes and no screen (ADR-016 to ADR-019). M6.5 plans the screens. Three things make them different from M6 core:

- Some screens **write to the ledger**: an import can create promises and a customer, a void cannot be undone, a recall can append events, an acknowledgement appends an event. A click that writes must be deliberate.
- Some screens carry **statements that are the control**: "intact means the cited lines are unchanged since drafting; it does not mean the promise is still true" (threat model F31-4b) and "this check compares numbers only" (F33-9). A screen that hides the words undoes the control.
- The window has **no jsdom**: hooks and click handlers are rendered in no test (threat model F6-1c), so a write path cannot be tested by clicking.

## Decisions (all proposed, none built)

**1. Irreversible writes use an in-page two-step confirm, never `confirm()`.** *Context:* a void cannot be undone, an import can create a customer and promises, and the dialog plugin overrides `alert` and `confirm` so they fail in the window (deviation M6-22). *Decision:* a write opens an in-page confirm area that restates what will happen in fixed words (for example "Voiding cannot be undone. The promise stays in the ledger, marked void, and is left out of recall."). Only a second, separate click calls the route. Every ledger write goes through a pure action module whose function calls `invoke` only when it is handed a `confirmed` value that only the confirm reducer can produce; it is tested with a recording fake `invoke` (no call without confirmation, exactly one with it), and a source scan proves each writing route name appears in exactly one action module. *Reason:* the owner of a compliance ledger should never record a mistake by one stray click, and because the window has no DOM test, the guarantee has to live in pure code that a test can run. A fake `invoke` that is never called without a confirmation is something an interviewer can be shown. *Rejected:* `window.confirm` (broken by the plugin, and not styleable or testable); one-click writes with an undo (the ledger is append-only, so there is no undo); a typed confirmation word for every write (too heavy for routine acknowledgements).

**2. Fixed statements are pinned: the window shows its own constant, and the sidecar's string is pinned by a Zod literal on the same constant.** *Context:* the recall and blast-radius responses carry the F31-4b statement and scope, and the contradiction response carries the numbers-only statement, in words that code (not the model) fixes. *Decision:* the window defines each statement once (as `apps/desktop/src/fixedTexts.ts` does for M6 core) and renders it in body text, never in a tooltip or a collapsed section. The reply schema uses `z.literal` on that constant for the sidecar's field, so if the sidecar's sentence drifts, the reply fails to parse instead of showing different words. Static-markup tests (to be written) check the statement appears in every result state and in every item detail; the planned mutation proofs remove the `Statement` component from the results, and change the literal. *Reason:* the sidecar already puts the words in every result; the window can only undo that by hiding them or by showing a different sentence, and this makes both a failing test. Showing the window's own constant (rather than the string from the reply) means a hostile or broken reply can never change the words a person reads. *Rejected:* rendering the sidecar's string directly (a change on one side would go unnoticed); a tooltip or "learn more" link (DESIGN.md rule 2: statements are always visible).

**3. A ban on web storage in every window source.** *Context:* the screens will hold personal data (up to 200 user logins, F26-7), policy text (a pasted proposed file), and customer names. Today only the review queue's source files are scanned for `localStorage` and `sessionStorage` (`apps/desktop/scripts/reviewQueueSources.test.mjs`); no test covers the rest of `src/`. *Decision:* a new `apps/desktop/scripts/noWebStorage.test.mjs` scans every file under `src/` (tests excluded) for `localStorage`, `sessionStorage`, `indexedDB`, `caches.`, `document.cookie` and `navigator.storage`, and an ESLint `no-restricted-globals` rule is proved live in `apps/desktop/scripts/eslint-rules.test.mjs`. *Reason:* anything written to web storage lands in the webview's profile folder on disk, where ALIBI neither controls nor logs it. A test over all sources is the only way to keep personal data and policy text out of it. *Rejected:* trusting code review; scanning only the new screens.

**4. The import (approval) screen is Option A+; Options B and C are rejected.** *Context:* approval is typing `approved` in the Review column in Excel and importing the reviewed workbook (ADR-017 decision 1); ALIBI never saves a workbook (ADR-014 decision 10, CLAUDE.md Section 11); no review-queue source may name a writing route (F37-3). *Decision (Option A+):* an import screen in its own files: pick a draft from the export listing, open it with `draft_rows` (which, per decision 7, returns the run id), choose a customer (existing, or new with an explicit confirm), enter the sent date, **Preview** (the import with `preview: true`: every check and count, nothing written, no customer created), then a separate second step "Create N promises for this customer" using decision 1's confirm. The outcome shows counts, skip codes and `already_changed_since_draft`. The review queue's `APPROVAL_LINE` loses its "(the import screen comes in a later chunk)" clause. *Reason:* approval stays a human act on a file, so no model output and no stray click can create a promise; the preview shows the owner exactly what an irreversible import would do before it does it. *Rejected:* **Option B** (the queue shows the Review mark and offers to import): it puts a writing route next to the reading screen and needs the F37-3 source scan changed on purpose and ADR-021 decision 3 ("Review cell not returned") amended; revisit after the import screen exists. **Option C** (approve inside ALIBI): ALIBI would have to save a workbook, against ADR-014 decision 10 and CLAUDE.md Section 11, and ADR-017 decision 1 already marks it a later extension.

**5. G35: an acknowledgement records the recall state the owner saw, with no ledger schema change.** *Context:* an `acknowledged` event carries no state today (ADR-017 "Chunk 2e: details the build settled" item 10), and a ledger with a different schema version fails closed and is left byte-identical (item 7 of "Chunk 2b", mutation proof 2b-v), so a schema change would stop every existing ledger from opening. The `promise_event` table already has `state` and `detail_code` columns (code: `sidecar/src/grc_sidecar/repositories/sqlite_ledger_repo.py::_SCHEMA`). *Decision:* the acknowledge request carries `seen_recall_event_id`. A new repository method appends the `acknowledged` event in one transaction only if the promise's latest `recall_state_changed` event has that id, copying its `state` and `detail_code`; otherwise it refuses with `422 recall_refused` and the new code `acknowledge_stale` and writes nothing. `SCHEMA_VERSION` stays 1. "No longer the latest" means a later recall event exists. Read responses gain `acknowledged_event_id`, `acknowledged_state` and `acknowledgement_current`. Old acknowledgements with no state stay readable and are shown as "acknowledged before ALIBI recorded the state seen". *Reason:* the ledger already had a place to store the state; what was missing was a rule that an acknowledgement names the state it answers and a check that the state has not moved underneath the owner. It is an append with a precondition, not an update, so ADR-017 decision 8 holds. *Rejected:* adding a column (a schema change that locks out every existing ledger); a separate `acknowledged_state` table (a second append-only store for one field).

**6. `flags_now` on each blast-radius item (F32-2).** *Context:* the flags shown are the proposed ones only, so the owner cannot tell whether a flag is new (ADR-018, Consequences). *Decision:* each item also carries `flags_now`, the flags of the current file, taken from the "now" result the service already computes; the window works out "new" as the proposed flags minus `flags_now` in a pure, tested function and marks a new flag. *Reason:* the sidecar already runs the check on the current file, so the data costs nothing; deriving "new" in the window keeps the response simple. *Rejected:* a computed `flags_new` field (it duplicates state the window can derive and a test can check).

**7. The draft reply carries the full `run_id`.** *Context:* the import needs the full hex run id (ADR-017 decision 2); after ALIBI is closed the window does not know it, the draft's file name carries only 8 hex digits, and the draft route returns `model`, `file_name`, `complete`, `question_count` and rows but no run id (code: `ledger/draft.py::DraftRows`, `api/questionnaire.py::DraftResponse`). *Decision:* add `run_id` to both, taken from the run record found by its full recorded `file_name`. A run is never matched by the 8-hex prefix (ADR-021 decision 2, F38-1d); a renamed draft still gets `run_record_missing`. *Reason:* the record is already looked up for the draft rows, so returning its id adds no new lookup and no new trust. *Rejected:* an import keyed by file name (it rewrites ADR-017 decision 2); the window keeping the id in memory (lost when ALIBI closes).

**8. `GET /ledger/cited-paths`.** *Context:* blast radius needs a vault-relative path, and a typed path is the cause of the mistyped-path threat F32-2. *Decision:* a read-only route returns the distinct stored `source_path` values of live promises with their counts, capped at 2,000 and refused whole above it; the blast-radius screen offers them as a choice. *Reason:* the owner can only get a useful preview for a path some promise cites, so offering exactly those paths removes most typing mistakes. *Rejected:* a free-text path (a typo finds nothing, and "nothing breaks" is then misread as "safe").

**9. A cap on `locations`.** *Context:* a `moved` result lists every place the quote occurs (ADR-017 decision 17), so recall and blast responses have no upper bound today and no closed worst-case size. *Decision:* at most 20 locations per item, plus an integer `locations_not_listed`. *Reason:* a response with a bound can be given a cap the proxy can enforce. *Rejected:* an unbounded list (a hostile or repetitive policy could make a response arbitrarily large).

**10. A `coverage` field on the blast-radius report.** *Context:* blast radius covers promises only; controls and linking documents are not built (ADR-018, G36), and no response field states that scope, which is why F32-4 is "No mitigation". *Decision:* a fixed `coverage` sentence on the report ("promises only; controls and linking documents are not checked"), shown by the screen next to the results. F32-4 may become Mitigated only when the field and its screen test exist. *Reason:* a scope that lives only in an ADR is invisible to the person reading the result. *Rejected:* leaving the statement to the screen alone (the sidecar response would still be readable as complete).

**11. `preview` on import.** Covered in decision 4: the flag runs every check and count, writes nothing, creates no customer, and appends no event. Mutation proof planned: a preview that creates the customer fails the "ledger bytes unchanged" test.

**12. `page_size` on the promises list.** *Context:* a page of 100 promises can be megabytes if answers are long (about 21 MB worst case by arithmetic from the bounds; not measured). *Decision:* the list takes a closed-range `page_size` (proposed 1 to 100) and the proxy keeps a 4 MiB response cap; a page over the cap makes the proxy answer `too_large`, and the ledger screen shows "This page of promises is too large to show. Choose a smaller page size." *Reason:* the owner can recover from a large page without any change to the sidecar's limits. *Rejected:* raising the proxy cap to the worst case (about 21 MB buffered in the host).

## Consequences

- Several accepted ADRs get dated "Addendum (2026-10-18)" sections: ADR-017 (G35, preview, item fields, cited-paths, locations cap, `page_size`), ADR-018 (`flags_now`, `coverage`, locations cap, the proxied request cap), ADR-019 (start-then-poll), ADR-020 (route table growth), ADR-021 (`run_id`, `APPROVAL_LINE`). ADR-005 gets nothing: no command and no capability entry changes.
- Tests that change on purpose: `sidecar/tests/test_ledger_store.py::test_an_event_outside_the_fixed_vocabulary_is_refused` (the acknowledged-with-state case); `sidecar/tests/test_ledger_hygiene.py` `EXPECTED_REQUEST_FIELDS` (cited by threat-model row G38); the owner-literal test of `APPROVAL_LINE` in `apps/desktop/src/components/reviewQueue.test.tsx`.
- Threat-model rows F39 to F44 are planned, all "No mitigation (planned, M6.5 chunk 65x)".
- **Limits stated now:** hooks and click handlers are still rendered in no test (F6-1c); the write guarantee is in the pure action module, not in a click. A "dropped on leaving the screen" claim for personal data would need a tested pure reset, so no screen says it (it says "ALIBI does not save or log them"). Hand checks in the bundled debug window are the owner's.
