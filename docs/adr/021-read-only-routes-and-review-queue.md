# ADR-021: Read-only routes and the review queue (M6 core)

Status: **Accepted. Built in M6 core** (marked at the 6i close, 2026-10-16): the sidecar routes in chunk 6b (PR #40, `419afbb`), consumed by the window in chunks 6g and 6h (PR #46 `843f11e`, PR #47 `2e4bcf2`). It was written in chunk 6a2 as "Proposed, planned". The names built are `POST /questionnaire/draft` (host route `draft_rows`), `POST /vault/index` (`vault_index_start`) and `GET /vault/index/{job_id}` (`vault_index_status`); refusals use a new `DraftRefusedError`, not the import's `ImportRefusedError` (decision 5's open choice), and `cell_unchanged` moved to `ledger/reviewed.py` so the import and the draft route share one definition. Every screen is verified in a **debug build only until M8**, and the owner's close checklist in the real window had not been run when this was marked built. Evidence is in the threat-model rows F36, F37 and F38 and in "Mutation proofs (M6)" at the end of this file. The design is from `M6_PLAN.md` (revision 2) A.3, C.5, Check 4 and J9 to J12; the facts about the run record come from a read of `repositories/base.py` and `questionnaire/writer.py` (a code read, **not run**). The checklist's results (owner hand check, 2026-10-16, one machine; observations, not tests) are in the threat model (F5-1b, G12) and in `M6_PLAN.md` ("M6 close check results"), recorded in PR #51 (chunk 6k).

## Context

Three things are missing for the M6 screens, and a sidecar change is the smallest way to give each.

- **No route returns per-row questionnaire results.** The status route returns counts and a summary. The answer text lives only in the draft workbook, and the ledger's run record ([ADR-017](017-promise-ledger-run-record-and-recall.md) decision 15) holds, for every question row, the final status, the reason codes, the citation (vault-relative path, lines, quote) and the hashes `question_sha256`, `answer_cell_sha256`, `status_cell_sha256`, `evidence_cell_sha256`, `cited_lines_sha256` and `cited_file_sha256`. It holds **no** question text, answer text, Reason text, Confidence text or Review text, so the Reason and Confidence cells of a workbook cannot be verified.
- **No route builds the vault index.** `Indexer.sync` is called only by the pack loader. [ADR-014](014-questionnaire-files-and-runs.md) decision 17 says a production "build index" trigger "belongs with the M6 folder picker". Without it a user meets `409 index_not_built` forever.
- **After ALIBI is closed the window does not know a draft's full run id.** The draft's file name carries only the first 8 hex digits (`<stem>-UNREVIEWED-DRAFT-<run8>.xlsx`), the in-memory run list is gone (ADR-014 decision 16) and no route lists run records.

The product brief's promise is *backed* answers. A review queue that shows an answer and a citation is only honest if the citation is ALIBI's record and not text someone could have edited in the workbook.

## Decision (built in M6 core)

**1. One new read-only route, `POST /questionnaire/draft` (the host route is `draft_rows`).** The body is `{file}` only (`extra="forbid"`). The route reads the draft from the export folder with the same loader calls as the ledger import (`read_input_bytes` in `questionnaire/loader.py`, then `load_questionnaire`, which runs `scan_package` and parses the same bytes; the ledger import makes those two calls in `ledger/service.py`), joins the run record, and returns every question row, up to the engine's 500-question cap. It never saves a workbook (the writer stays the only saver, [ADR-014](014-questionnaire-files-and-runs.md) decision 10), writes no event and no file, and logs no content at any level. Sits behind the same authentication as every route.
*Reason:* the queue has to show the answer and its source side by side, and the only places that hold them are the workbook (text) and the run record (verdicts and citations). A read-only join of the two, checked by hash, gives the screen both without letting either be trusted blindly.
*Rejected:* **reading the answers out of the workbook in the window**, because the window has no file access and must not parse workbooks; **adding answer text to the run record**, because that changes shipped M5.5 storage and puts more content at rest; **returning the Evidence cell as the citation**, because it is editable text.

**2. Keyed by the draft file name, found by the full recorded `file_name` only (owner answer J9).** The host lists the export folder and the window picks a name. The sidecar finds the run record by its recorded `file_name`. **Chunk 6b first reads the ledger repository and reports whether that lookup exists; if it does not, 6b adds the smallest read-only lookup** (a read method only, so the ledger stays append-only, [ADR-017](017-promise-ledger-run-record-and-recall.md) decision 8). **A run is never matched by the 8-hex prefix in the file name.** A renamed draft has no record under its new name and is refused with `run_record_missing`, which is the safe behaviour. A `run_id` field for renamed copies is not in M6 core. Output names are created with exclusive create (ADR-014 decision 10 (f)), so a name is unique per export folder; 6b's plan confirms this.
*Reason:* the window cannot know the full run id after a relaunch, and a 32-bit prefix is a guess, not an identity. Matching on the full recorded name means a wrong match is impossible by construction.
*Rejected:* **keying by `run_id`**, because it is not known after a relaunch; **matching by prefix**, because two runs can share it and a renamed file would match the wrong one.

**3. Where each field comes from (the per-field table).**

| Field | Source | Trust rule |
|---|---|---|
| `row` | run record (`RunAnswer.row_index`) | code's |
| `question_text` | **workbook**, the question cell | its hash is compared with the record's `question_sha256`; **any mismatch, or a different number of question rows, refuses the whole response** (`question_mismatch`, integer counts only), as the import does |
| `status` | **run record**, the final status | code's; **never read from the workbook** |
| `status_edited` | workbook Status cell hashed and compared with `status_cell_sha256` | `true` when they differ (decision 4) |
| `reasons` | **run record**, reason codes | code's; the workbook's Reason cell is **not read** (the record has no hash of it, so it cannot be verified) |
| `answer_text` | **workbook**, the Answer cell, only when the record says an answer was written | plain text, untrusted |
| `answer_edited` | Answer cell hashed and compared with `answer_cell_sha256` | `true` when they differ |
| `citation` (`source_path`, `start_line`, `end_line`, `quote`) | **run record only**; never parsed from the Evidence cell | code's; `null` when the record has none |
| `evidence_edited` | Evidence cell hashed and compared with `evidence_cell_sha256` | `true` when they differ; the screen then warns that the citation shown is ALIBI's record, not the cell |
| Confidence cell | not returned | no hash exists and the model's self-rating decides nothing |
| Review cell | not returned in M6 core | approval is a M6.5 screen (ADR-017 decision 1) |
| Header: `model`, `file_name`, `complete`, `question_count` | run record | code's |

Whether the Status-cell comparison works for a blank row (`status_cell_sha256` is non-null even then) and whether the import's `reviewed.py` can be reused unchanged were not verified when this was written; 6b settled both: the blank-row comparison is tested (see Consequences), and the import's `cell_unchanged` was moved into `ledger/reviewed.py` and is shared by the import and the draft route (PR #40 body).
*Reason:* a verdict or a citation read from a cell would let a hand edit, or hostile text in a cell, appear as ALIBI's finding. Taking them from the record, and using hashes only to say "this cell differs", keeps the code's verdict apart from the file.

**4. An edited Status cell shows the record's status, labelled (owner answer J12, deviation M6-6).** For a row where `status_edited` is true the queue shows the run record's status labelled "recorded by ALIBI", plus the fixed line "The Status cell in the workbook was changed after drafting. The code's verdict is shown, not the cell." The edited cell's text is **never** shown as the verdict, and the route does not even return it. The row sorts first, like `NEEDS_REVIEW`. The `status_recorded` field of the earlier plan is dropped: `status` is always the record's. **An edited Answer cell is labelled too:** when `answer_edited` is true the screen shows the answer with the fixed line "The Answer cell was changed after drafting. The citation belongs to the original answer." The citation shown is still the run record's, never the cell's.
*Reason:* hiding the status would hide what ALIBI actually concluded; showing the edited cell would present an edit as the code's verdict. Labelling the record and saying the cell changed shows both facts and keeps one of them clearly not a verdict.

**5. No run record means a refusal, not a degraded read.** Without the record nothing in the workbook can be verified and the Evidence cell may not stand in for a citation. Typed errors, fixed words only, no text: `503 ledger_root_not_configured` when no ledger folder is in use; `503 export_root_not_configured`; `404 file_not_found`; `422 draft_refused` with a code: `run_record_missing` (the ledger has no record for this draft, including a run made without a ledger, `run_record_not_kept`), `headers_changed`, `question_mismatch` (with counts) and the loader's own refusal codes. A refusal returns no rows. **One edited question cell refuses the whole queue:** the question cells are compared by hash with the record (decision 3), so a single changed question (or a different number of question rows) gives `question_mismatch` and no rows at all, not a queue with one row missing. The screen explains this in plain words, for example "A question in this file was changed after drafting, so ALIBI cannot match the rows to its record and shows none of them. Open the original draft instead." (wording to be fixed in chunk 6h; the plain-words requirement is the decision). Whether to reuse the import's `ImportRefusedError` codes or add a `DraftRefusedError` is decided in 6b's plan. The screen turns each into a fixed message, and `run_record_missing` tells the user how to avoid it (set the ledger folder, restart ALIBI, run again, per [ADR-020](020-host-proxy-folders-polling.md) decision 5).
*Reason:* a draft with no record looks the same as one with a record until someone opens it; refusing keeps "verified against ALIBI's record" from ever meaning "looked plausible".

**6. Two routes to index the vault: `vault_index_start` and `vault_index_status` (job plus poll, owner answer J3).** `vault_index_start` is a POST with an empty body (`extra="forbid"`) that takes the **shared heavy-job slot** (the one slot for a questionnaire run, a contradiction run and now an index job, ADR-014, `M55-13`) and passes the **model gate** for the embedding model, then answers `202 {job_id}`. It answers `409 run_in_progress` if the slot is taken, `503 models_unavailable` (naming the missing models) if the gate refuses, and `503 vault_root_not_configured` if there is no vault. `vault_index_status` is a GET with the job id (the pattern `^[0-9a-f]{8,64}$`) and returns `{status, files_done, files_total, ...}`: fixed words and integers only, never a path or text, and `404` for an unknown id. Both work through the existing indexer; neither reads outside the vault or writes outside the index folder. The final field names are fixed in 6b's plan.
*Reason:* indexing a vault can take minutes, so a start that returns a job id and a status that is polled avoids a long proxy timeout and matches how a questionnaire run is shown. Using the shared slot means an index job cannot run beside a heavy model run.
*Rejected:* **one long request**, because the proxy would need a long timeout and the window could not show progress; **a second, separate job slot**, because [ADR-014](014-questionnaire-files-and-runs.md) allows one heavy job at a time on purpose.

**7. The queue reads and orders; it records no approval, and it does not prove relevance.** Rows are ordered by risk: edited-status rows and `NEEDS_REVIEW` first with the code's reasons, then `PARTIAL`, then `SUPPORTED`. Each row shows the question, the draft answer, and the source file, exact lines and verbatim quote side by side. On every `SUPPORTED` or `PARTIAL` row the screen shows the fixed sentence: "The quote is real company text that was in the context. ALIBI has **not** checked that it answers this question." Approving stays what it is: typing `approved` in the Review column of the workbook and importing it (a M6.5 screen). A "mark approved" button would need ALIBI to save a workbook, against ADR-014 decision 10 and CLAUDE.md Section 11; the screen says so in a fixed line.
*Reason:* the queue is a way to read the verdicts, not a verdict. F12-2c (a true quote that does not answer the question) has no code control, so the screen must not look like one.

## Consequences

- The sidecar gains three routes (`POST /questionnaire/draft`, `vault_index_start`, `vault_index_status`), all read-only with respect to the vault, the ledger and workbooks (the index job writes only the index folder, as the indexer already does). The proxy table of [ADR-020](020-host-proxy-folders-polling.md) gets three variants.
- The review queue needs the **ledger folder** and a run record. The ledger folder must be set before the first run if the user wants the queue; the folders screen and the Start button say so (F37-5).
- F12-2c and F12-4c **stay No mitigation** as code controls: the human review the queue provides has no completion check. Their rows were reworded at the 6i close to say the queue is built and is human review with no completion check, and the first live run of the queue (one run, one machine, counts) is recorded in the F12-2c row; the measured counts (blank-labelled items answered 4, 5 and 3 of 9 in three held-out runs, ADR-013 live check B) are kept as cited.
- The response can be up to 4 MiB (500 rows); the host's cap for `draft_rows` follows.
- **The first real index build was a live check run by the owner** (2026-10-16, PR #48 body): 12 files and 52 chunks from the synthetic demo vault, on a real Ollama. Chunk 6b itself tested the index routes with a fake embedder, which is why a real build needed that run; it is an observation, not a test.
- **Cloud `sqlite-vec` (not answered):** the 6b session ran in a cloud Linux environment; the PR #40 body does not say whether the extension loaded there or which indexer tests skipped. The evidence that counts is the owner's local Windows run (PR #40 body: pytest 3237 passed on Windows) and the air-gap container run (3224 passed, 13 skipped, all skip reasons on the allow-list).
- **Tests built in chunk 6b** (the threat-model rows F38-1 to F38-4 and F37-4c list the exact `path::test_name` references): the response status, reasons and citation equal the run record when the workbook cells are rewritten; the `status_edited`, `answer_edited` and `evidence_edited` flags are hash comparisons; a draft from a run made without a ledger returns no rows; two records that share a prefix return only the exact match; a canary at DEBUG shows no content; a held heavy-job slot refuses the index start with 409, missing models with 503; an unknown job is 404. The question the first version of this ADR left open, whether the Status-cell comparison works for a blank row, is settled: the draft tests include a `NEEDS_REVIEW` blank row whose Status cell is compared too (`sidecar/tests/test_draft_routes.py::test_an_untouched_draft_returns_the_records_rows_and_no_edit_flags`, `::test_draft_status_comes_from_the_record_not_the_status_cell`). The mutation proofs are in the last section.
- **Not in this ADR:** the ledger, recall, blast-radius, contradiction and reality screens (M6.5), a `run_id` field for renamed copies, a per-row status during a run (the status route stays counts only; the queue reads the finished draft), and any approval control.
