# ADR-020: Host proxy, saved folders and polling (M6 core)

Status: **Proposed. Planned, nothing in this ADR is built.** It is written in chunk 6a2 and built in chunks 6d (proxy), 6e (folders, dialog plugin, path checks), 6f and 6g (window). Each decision below is marked planned until its chunk merges, and the chunk that builds it changes the mark and records its evidence. Everything here applies to a **debug build only until M8**: release builds cannot start the sidecar (`start_dev` is debug only), so no M6 screen exists in an installed app. The design is from `M6_PLAN.md` (revision 2) sections B, E and F. Starting values for caps and timeouts are **unmeasured**.

## Context

Today the window can ask the host one question, `sidecar_health` ([ADR-005](005-webview-csp-and-capabilities.md), [ADR-006](006-window-status-polling-and-ipc-contract.md)). The sidecar has questionnaire, ledger, reality and contradiction routes, but nothing in the host or the window can reach them, and the sidecar knows only the folders in its environment. M6 core needs the window to choose folders, index the vault, run a questionnaire with progress and read a finished draft. Four facts shape the design.

- The auth token and the sidecar's port live only in Rust (CLAUDE.md 3.4). The CSP's `connect-src` lets the window reach only `ipc:` ([ADR-005](005-webview-csp-and-capabilities.md) decision 1), so the host is the only caller of the sidecar.
- The sidecar reads its settings once at startup (CLAUDE.md 5.1) and the folder-overlap and allowlist tests rely on that. The host has no restart path: [ADR-004](004-host-sidecar-lifecycle.md) says "`Failed` and `Stopped` are terminal" and "nothing returns to `Starting`", and [ADR-006](006-window-status-polling-and-ipc-contract.md) decision 4 says "the host has no restart path in M2".
- The status route already returns `completed` and `total` while a run is going (`M6_PLAN.md` Check 1, a code read, not a run).
- CLAUDE.md 3.6 asks for a path check in both layers. The sidecar's `resolve_within` exists; the Rust half (G9) does not ([ADR-009](009-vault-indexing-contract.md)).

## Decision (all planned)

**1. One command, `sidecar_call`, with a closed route table (planned, 6d).** The window sends a `Route` value from a closed enum plus that route's typed arguments. Rust holds a static table: for each variant the HTTP method, a fixed path template (only a run or job id matching `^[0-9a-f]{8,64}$` is substituted), a typed request struct (`deny_unknown_fields`), a request cap, a response cap and a timeout. The window never supplies a URL, header, method or port. The M6 core table has seven variants: `readiness`, `questionnaire_inspect`, `questionnaire_start`, `questionnaire_status`, `vault_index_start`, `vault_index_status`, `draft_rows` (the last three are the new sidecar routes of [ADR-021](021-read-only-routes-and-review-queue.md)). Ledger, recall, blast-radius, contradiction and reality routes are added in M6.5. The host rebuilds the request body from its typed struct and does not forward the window's text.
*Reason:* the token and the port stay in Rust, so the window can only ask for named operations. One command with a closed table gives the capability file one entry and gives the tests one table to check; separate commands would give no extra security (they all go to the same window) and more places to drift.
*Rejected:* **a command per route**, because it multiplies the three places that must agree (ADR-005 consequences) with no gain; **a command that takes a path or URL**, because the host would become an open relay to the sidecar.

**2. Caps and timeouts per route (planned, 6d).** Request bodies are limited to 16 KiB and checked before sending. Responses are limited to 1 MiB (`draft_rows` up to 4 MiB, from the sidecar's 500-question cap) and refused if the declared length or the bytes read pass the cap, including chunked bodies. Timeouts, starting values: connect 2 s; `readiness` and `questionnaire_status` 5 s; `questionnaire_inspect` 60 s; `questionnaire_start` 60 s (it checks the models and reads a digest); `vault_index_start` 30 s; `vault_index_status` 5 s; `draft_rows` set in chunk 6b (60 s as a start). This closes backlog G34 **only for the proxied path**: another local process that holds the token can still send an oversize body straight to the sidecar.
*Reason:* the host sits between the window and the sidecar, so it is the one place a limit protects memory on both sides. Per-route values keep a fast status poll from waiting as long as a workbook read.
*Rejected:* **one global timeout**, because a 5 s poll and a 60 s read need different limits; **a limit in the sidecar only**, because it would parse an oversize body before refusing it (G34), and a sidecar limit is a separate decision.

**3. Errors that carry no text (planned, 6d).** A closed `ProxyError` enum of unit variants (`not_ready`, `unauthorized`, `unreachable`, `timeout`, `too_large`, `bad_request`, `bad_response`, `internal`) is serialized as `{"error": ...}`, with a committed contract fixture, an exhaustive-match test and `size_of <= 1`, the pattern of [ADR-006](006-window-status-polling-and-ipc-contract.md) decision 3. A sidecar reply passes to the window as `{status, body}` only if the status is in an allowed set, the body is within its cap and is valid JSON; the window parses it with a strict Zod schema per route that lists every error code. `HealthClient::build` becomes a shared sidecar client (`no_proxy`, no redirects, sensitive header, a port-only endpoint); `sidecar_health` keeps its fixed reply.
*Reason:* an error string can echo a path, a token or document text, so errors are words from a fixed list. A fixture both sides test means a new variant breaks the Rust build, then the Rust fixture test, then the Vitest suite, "until the enum, the fixture and the schema agree" ([ADR-006](006-window-status-polling-and-ipc-contract.md), Consequences).
*Rejected:* **passing the sidecar's error text on**, because it can quote input; **a free-text `detail` field**, for the same reason.

**4. Polling, not a relayed event stream (planned, 6f and 6g).** The window calls `questionnaire_status` about once a second through `sidecar_call`. There is no Tauri `Channel`, no event permission and no Server-Sent Events parser in Rust. The sidecar keeps serving SSE ([ADR-014](014-questionnaire-files-and-runs.md) decision 16); the host does not relay it. The screen handles four behaviours read from the code: `completed` moves only when a question finishes (a local "time since the last answer" counter, never "stuck"); after the last answer `status` is still `running` while the file is written ("writing the answers file", not "done"); a model that goes away mid-run blanks the rest at once and ends `stopped`; an unknown run is `404 run_not_found`.
*Reason:* the status route already carries the real counts, so a poll gives true progress with fewer moving parts and no new permission. The cost is up to one second of delay, which is small next to a 40 to 60 second answer.
*Rejected:* **a Rust SSE relay**, because it needs a streaming parser, a channel and a wider capability for no more information; **a host event pushed to the window**, which ADR-006 said needs its own core event permission.

**5. Folders are saved by the host and applied on the next launch (planned, 6e and 6g).** A small JSON file in the app config directory holds the five folders the user chooses (vault, questionnaires, exports, imports, ledger). The host chooses the index and log folders. The window never gives the sidecar a path; it asks the host to pick a folder of a named kind (an enum) and receives the validated folder's display path or a typed error. A saved change takes effect the next time ALIBI starts, because the sidecar reads its settings once. The screen shows two columns, **In use now** and **Saved for next launch**, and says "Saved. Takes effect the next time you start ALIBI." There is no restart path and no new host state.
*Reason:* the folders are the app's authority over the user's files, so the host, not the webview, decides them. Applying them at the next launch keeps "the sidecar reads its settings once", which the folder-overlap and allowlist tests rely on.
*Rejected:* **restarting the sidecar when a folder changes**, because it adds new host state and re-opens the lifecycle tests ([ADR-004](004-host-sidecar-lifecycle.md)); **letting the window hold or submit paths**, because a compromised window could then name any folder.

**6. Seven folder settings, a nine-key environment (planned, 6e).** The child environment is `env_clear()` and then exactly nine keys: `SYSTEMROOT`, `GRC_AUTH_TOKEN` and seven folder variables (`GRC_VAULT_DIR`, `GRC_INDEX_DIR`, `GRC_LOG_DIR`, `GRC_QUESTIONNAIRE_DIR`, `GRC_EXPORT_DIR`, `GRC_IMPORT_DIR`, `GRC_LEDGER_DIR`). The index and log keys are always present; the five user folders are optional and absent when not set or not valid. The debug-only fallback of [ADR-009](009-vault-indexing-contract.md) (host variable `GRC_VAULT_DIR`) is kept and used **only when no vault is saved**; a saved vault wins; a release build never reads it. The environment tests that pin five keys are re-pinned to nine in 6e.
*Reason:* a fixed list of names is what lets a test prove nothing else (a proxy variable, a home directory) reaches the sidecar. The user folders are optional because "not configured" is a valid state the sidecar already reports.
*Rejected:* **passing the parent's environment through**, which would forward proxies and secrets; **a settings file read by the sidecar**, because the sidecar would then take a path from somewhere other than the host.

**7. Validated on set and on every start, in both layers (planned, 6e).** When a folder is set, and again at every start, the host canonicalizes it (reusing `dev_paths::existing_directory`, which refuses UNC, device and non-drive verbatim paths), requires a directory, and applies the **same overlap rules as the sidecar's `Settings`** (equal, inside or containing, pairwise among vault, index, questionnaire, export, import and ledger, checked with `starts_with` on canonical paths). A folder that is invalid at start is **not passed** (its key is absent, so the sidecar reports "not configured") and the host records a typed reason the screen shows. A file name from the window (questionnaire or export) is checked as one path component (no separator, `..`, drive, colon, NUL, reserved device name, over 260 characters), then `canonicalize(root.join(name))` must `starts_with(root)` and be a regular file before the request is forwarded. The sidecar repeats its own `resolve_within` and `validate_runtime_dirs`. This closes G9 and, with chunk 6c's Python junction test, the junction case of G10.
*Reason:* a saved file can be edited between launches (a same-user process, accepted as O1), so a folder is re-checked every start, and a check in only one layer is a single point of failure (CLAUDE.md 3.6).
*Rejected:* **validating only when the folder is chosen**, because the file can change afterwards; **dropping an invalid folder silently**, because the user would not know why a screen says "not configured".

**8. The dialog plugin is used only from Rust (planned, 6e).** `tauri-plugin-dialog` is registered in `lib.rs` and called from Rust; **no dialog permission is granted to the window**. The command list grows to exactly `sidecar_health`, `sidecar_call`, `folders_get`, `folder_pick` and `folder_list_files` (provisional names), and the capability file lists exactly the matching `allow-*` entries. The tests in `security_config.rs` change on purpose in 6e (`M6_PLAN.md` E.1): the exact command list and capability; a new test that no permission string contains `:` or starts with `dialog`, `core`, `opener` or `fs`; a new test that `tauri-plugin-dialog` is the only `tauri-plugin-*` dependency and has an exact `=` pin; and a test that no command takes or returns a path the window can submit back. Each is checked with a mutation proof (add `dialog:default` to the capability, require failures) and a runtime probe in the bundled debug build that `plugin:dialog|open` from DevTools is rejected as not allowed. A dedicated `FailureKind` (provisional `index_dir_unavailable`) replaces the reuse of `EnvRejected` (G8, [ADR-011](011-startup-model-check.md)); the count of failure kinds goes from 24 to 25 and `health-contract.json`, `health.ts` and its test change together.
*Reason:* a picker is the only way a user names a folder without typing a path, but a dialog the window can call would hand the window a path as authority. Keeping the plugin behind a Rust command means the window only ever receives a display value.
*Rejected:* **granting `dialog:default` to the window**, because the window would then open dialogs and hold paths; **typing paths into a text box**, which is error-prone and gives the window the same authority.
*Not verified:* the plugin's exact pinned version, license and telemetry behaviour (not looked up; stated at install time in 6e), whether it needs a `plugins` entry in `tauri.conf.json`, and its JavaScript command name for the probe.

**9. Debug build only until M8 (planned wording, applies to every M6 chunk).** Chunk reports, PRs and docs say "debug build", never "the app" or "the installer", where that matters. Every M6 screen is verified in a bundled debug build run from the repository with the dev sidecar.
*Reason:* claiming an installer exists would be a claim the code cannot back.

## Consequences

- The window gains four more host commands and a capability with five entries. The token and the port still never reach it, and a window that is compromised can still only ask for named operations with typed arguments.
- **A saved folders file is a new input.** A same-user process can edit it (O1, accepted). The start-time re-validation and the sidecar's own checks limit what an edit can do; they do not stop the user's own account.
- A change of folder needs a restart of ALIBI. The two-column screen says so; the cost is a slower first-time setup (set the ledger folder, restart, then run).
- Polling adds one local request per second while a run is going; the sidecar answers from memory.
- G34 is closed for the proxied path only. G8, G9 and G11 close in 6e and 6f; G29 (Rust half) in 6d.
- The host will read `/readiness` every 5 s while healthy, so [ADR-011](011-startup-model-check.md)'s "the host does not read `/readiness` yet" stops being true in 6d and 6f.

## Known limits and unverified items

- Caps and timeouts are starting values, not measurements.
- Whether `tauri-plugin-dialog` needs a `plugins` entry; its version, license and telemetry; its JS command name (all 6e).
- Whether release builds ship DevTools (checked in 6i).
- Whether a Rust test can create a Windows junction without privilege: not needed, Rust junction tests are omitted and the Python test of 6c covers the scanner.
- The threat-model rows that name the tests for this ADR are F34 and F35 (planned, written in chunk 6a2).

Revisit if: a screen needs instant updates (then add a host event with its own permission); the host gains a restart path (then folders can apply at once, and the "next launch" text and tests change); a second window or plugin is added; or M8 lets a release build start the sidecar.
