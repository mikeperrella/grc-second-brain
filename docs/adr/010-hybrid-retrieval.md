# ADR-010: Hybrid retrieval, a lexical FTS5 table beside the vectors

Status: Accepted. The store is M3b. Query building and lexical search are M4d, the merge and typed results M4e, the budget, quota, withdrawn handling and expansion M4f, and CLAUDE.md 8.2 and the Section 9 M4 row were updated in M4g. Items 3 and 4 of the Decision below describe the M3 state (M3 exposes no lexical query method and "M4 owns the query builder"); the sections after "What the tokenizer does not do" describe what M4 built.

## Context

Questionnaire questions and policy text are full of exact identifiers: `AC-2`, `AC-2(1)`, `CC6.1`, `A.5.15`, `IA-2`, `3.1.1`. An embedding blurs them (`AC-2` and `AC-20` are near neighbours in vector space), while an exact word match finds the one control a question names. The reverse holds for paraphrase: "multi factor authentication" and "MFA" are close as vectors and unrelated as words. So the index keeps both, and retrieval can use both.

## Decision

1. `fts_chunks`, an FTS5 virtual table over the chunk text and heading path (identifiers often sit in headings such as "AC-2 Account Management"), lives in the same SQLite file as `chunks` and `vec_chunks`. Its rowid equals `chunks.rowid`. `replace_document`, `remove_document` and `begin_sync` write and delete it in the same transaction as the chunks and vectors (ADR-009), so a lexical hit can never come from a version of a file the vector side no longer has.
2. **Tokenizer: `unicode61 tokenchars '-'`.** The hyphen is a token character, so `AC-2` is one token. The dot is a separator, so `CC6.1` is the two tokens `cc6` and `1`, and a phrase query (`"CC6.1"`) matches them adjacent.
3. **Identifier queries must be phrase-quoted** (`"AC-2(1)"`, not `AC-2(1)`). Unquoted, FTS5 reads `-`, `(` and `.` as syntax. M4 owns the query builder and must quote.
4. M3 exposes **no lexical query method**. The tests query the table directly. Nothing in M3 scores, merges or ranks lexical hits.

## The tokenizer comparison (spike, 2026-10-09)

Method: a small synthetic corpus of heading-like and sentence-like rows, including longer-identifier "trap" rows (`AC-20`, `CC6.10`, `A.5.152`, `3.1.10`, `13.1.1`), identifiers inside prose (`AC-2,`  `(AC-2)`, `CC6.1.` and `A.5.15.` at the end of a sentence), and a distractor row with the same characters spaced out (`AC 2`, `3 1 1`). Each query was run as an FTS5 phrase. Identical results on Windows (Python 3.11.9, SQLite 3.45.1) and in the `--network none` container (Python 3.11.16, SQLite 3.46.1). "Exact" means the rows that really cite that identifier. "Child" rows (`AC-2(1)` for `AC-2`) are counted as acceptable, not as errors.

Reading the table:

- **`tokenchars '-.'` (the first candidate in the M3 plan) is rejected.** A dot that is part of a token also sticks to a sentence-final dot, so `CC6.1.`, `A.5.15.` and `3.1.1.` become tokens that no identifier query can match. Policy prose cites controls at the end of sentences, so this is a silent miss on the most important inputs.
- **`trigram` is rejected.** It matches substrings, so every identifier also matches every longer identifier that begins with it (`AC-2` finds `AC-20`, `CC6.1` finds `CC6.10`, `A.5.15` finds `A.5.152`, `3.1.1` finds `3.1.10` and `13.1.1`). A hybrid search would then promote the wrong control with a lexical score that looks exact.
- **`unicode61` default** behaves like the chosen tokenizer on this corpus when queries are phrase-quoted, but treats `AC 2` and `AC-2` as the same, so spaced-out text (a part number, a date) matches identifier queries. Keeping the hyphen as a token character removes that class for the identifiers that use one. The distractor rows that remain for `CC6.1`, `A.5.15` and `3.1.1` come from the dot being a separator, which is the price of matching sentence-final identifiers.
- **A control ID's children are hits, deliberately.** `AC-2` finds `AC-2(1)` and `IA-2` finds `IA-2(1)`, because an enhancement belongs to its parent control. The reverse does not hold.

## What the tokenizer does not do (owned by M4)

- **`3.1.1` does not find `03.01.01`, and `5.15` is not guaranteed to find `A.5.15`.** These are different ways of writing one control. They are **query normalization, not tokenizer choice**: M4's query builder must expand an identifier into its known written forms (for example `3.1.1` into `3.1.1` and `03.01.01`; `5.15` into `5.15` and `A.5.15`) and OR them. The chosen tokenizer happens to match `5.15` against `A.5.15` as a side effect of the dot being a separator, which M4 must not rely on (the `-.` candidate, for instance, does not).
- **`multi-factor` and `multi factor` do not meet lexically.** The hyphen stays inside the token, so the hyphenated and spaced spellings are different tokens. Matching them is the job of the vector side of the hybrid search, where the two spellings embed close together. A lexical-only path would miss one of them, so a caller that needs both must not use the lexical table alone.
- Scoring (BM25 or otherwise), merging lexical and vector hits, and query syntax belong to M4.

## Query builder and lexical search (M4d, implemented)

`retrieval/identifiers.py` is a table of identifier rules (`nist-800-171-r3`, `iso-27001-annex-a`, `nist-800-53`, `nist-csf-2.0`, `soc2-tsc`, `generic-hyphenated`), each with a pattern and a function that returns the written forms (`3.1.1` and `03.01.01`; `5.15` and `A.5.15`; `AC-2(1)` and `AC-02(1)`; `PR.AA-01` and `PR.AA-1`; `CC6.1` and `SOC2:CC6.1`). It is format normalization only: nothing says two controls mean the same thing, and no form carries a revision. A test per row has positive and near-miss tokens. `retrieval/query.py` turns user text into an FTS5 MATCH string: the text is cut at 2,000 characters, control characters become spaces, words are split on whitespace, surrounding punctuation (quotes, brackets, Markdown `*` and `_`, sentence punctuation) is trimmed, a small fixed list of stop words is dropped (not `and`, `or`, `not`, `near`), identifiers are expanded to all their forms, at most 32 terms are kept, and **every term becomes one double-quoted FTS5 string with each inner `"` doubled**. The only syntax in the result is the ` OR ` the builder writes between terms: no parentheses, `*`, `^`, `:` or operators are ever generated, so `NEAR(a b)`, `a*`, `col:x`, `AND`, unbalanced quotes and the rest are literal words. A quoted string is tokenized by the same tokenizer as the index, so a phrase matches exactly what was indexed; a test compares the real `fts5vocab` terms of every identifier form with the independent oracle. Words are ORed and ranked by BM25 (`lexical_search`: parameterised `MATCH ?`, `ORDER BY bm25, chunk_id`, so ties never depend on insertion order). Limits: an identifier is recognised only as a whole whitespace-delimited word; the digits-with-spaces row (`3 1 1`) is still a false positive of the dot-as-separator tokenizer (above); a string such as `1.2.3` or `6.1` is treated as an identifier and also searched in its other forms (harmless noise); `control_mappings` in frontmatter are not searchable (frontmatter is not chunked), deferred to M5.

**Why the oracle is independent.** `tests/oracle_fts.py` re-implements the tokenizer from its definition and imports nothing from `grc_sidecar` (an AST test fails on any import, relative or aliased, and is itself tested on bad samples); if the builder had a bug, an oracle made from the same code would share it. `test_hostile_inputs_never_change_meaning` compares the rows found for 40 hostile strings with the oracle's, so a test that only checked "no exception" cannot pass for a builder that quietly changed the meaning.

## Hybrid merge, results and freshness (M4e, implemented)

**Pipeline** (`retrieval/service.py`, `Retriever.retrieve`; internal, no HTTP route or Tauri command in M4). In this order, which is the safety property: (1) `refresh_staleness()` on the vault index, before anything is read. If it cannot run, retrieval raises `RetrievalUnavailableError` and returns nothing; if there is no index file it raises `IndexNotBuiltError` (retrieval never builds an index: that needs the embedding model and can take minutes). A file edited since the last sync has lost its rows, so its old text cannot be returned; those paths come back in `withheld_unindexed` so a caller knows evidence was withheld, not absent. (2) The keyword query (above) runs in each store. (3) The vector side: `ModelGate.require(embedding model)` first (ADR-011), then the question is embedded and searched in each store. If the model is missing or Ollama is down the result is the keyword results with `mode="lexical_only"` and `degraded_reason` (`embedding_unavailable` or `embedding_model_missing`); it is never a silent fallback. A changed embedding model (profile mismatch), a dimension error or a store error is not downgraded: it raises, because the index needs a human. (4) Per store, the two lists are merged by Reciprocal Rank Fusion. Two stores, never mixed: the vault index and the packs index (ADR-008). The packs are verified when loaded, not per question. A question is one at a time (a lock), so opening an index and the freshness check cannot interleave.

**Reciprocal Rank Fusion** (`retrieval/fusion.py`): `score = sum 1 / (60 + rank)` over the lists a chunk appears in, ranks 1-based. K = 60 is the constant of the original RRF paper, fixed and not tuned here, so nothing in this ADR is a tuning claim. Why RRF: a BM25 score and a cosine distance are on different scales, so adding them would need a tuned weight; RRF uses only each list's order, has one fixed constant, and degrades to a single list. Determinism: each input list is sorted by (its own score, `chunk_id`) before ranks are assigned, scores are exact fractions (`fractions.Fraction`, so equal rank sums are exactly equal), and the output order is (-score, `chunk_id`) with `chunk_id` compared as plain text, which is locale-free. Known limit: rank-only fusion ignores how strong a match was, so a weak keyword rank 1 counts the same as a strong one.

**Typed result** (`retrieval/models.py`): every chunk carries `source_path`, line range, `text` (untrusted data, returned byte for byte; the 8.6 delimiters are applied when M5 builds a prompt), `source_kind`, `pack_id`, `doc_type`, `review_by`, `review_overdue`, its fused score and its rank in each list. `source_kind` is computed by code, never read from the document's own claims: `framework_reference` if the document was loaded from a pack (collection `pack:*`) **or** its declared type is `framework`, otherwise `company_policy`. A policy that says it is a NIST control stays company policy. `pack_id` lets a caller tell which pack (and so which revision, for example 800-171 Rev 3) a framework chunk came from. `review_overdue` uses the injected `Clock` and `vault/clock.py::is_stale` (due today is not overdue); stale documents are returned and flagged, not hidden, so M5 can cap an answer's status on them. Two meanings of "stale" exist and are named apart: a file changed after indexing (`withheld_unindexed`, rows deleted, never returned) and a review date that has passed (`review_overdue`).

**No relevance floor (known limit, decided: no threshold in M4).** Vector search returns its nearest rows however far away they are, so almost any question returns some company text (a test pins this with a nonsense question). **A non-empty result is not evidence.** M5 must decide "no evidence" itself (the verbatim-quote check, CLAUDE.md 8.4) and must never treat non-empty retrieval, a high fused score or `mode=hybrid` as support for a claim.

Repository addition: `documents_info(paths)` (collection, type, review date, doc id for each path).

## Budget, slots, framework quota, withdrawn controls, expansion (M4f, implemented)

**Context budget** (`retrieval/selection.py`; every number is a named constant). Starting point: the OWASP RAG Security Cheat Sheet's 3 to 5 chunks and 2,000 to 4,000 tokens. The client cannot tokenize with the generation model, so the budget is in **characters**: 4,000 tokens x 1.38 characters per token = **5,520 characters**, where 1.38 is the worst ratio measured for identifier-dense control text in this project (ADR-009; ordinary prose measured 5.55, so this under-fills on prose, which is the safe direction). It is an approximation, documented as such, and a request parameter (`char_budget`, with `max_chunks`, default 5) so M5 can change it once it has measured. A chunk is **never truncated** to fit (that would break the verbatim-quote check of 8.4): one that does not fit is skipped and the next is tried, and the skipped ones are listed in `budget.dropped_for_budget`. With the 2,300-character embedding cap only about two maximum-size chunks fit; typical sample-vault chunks are far smaller.

**Slots and the framework quota.** `max_chunks` is split into one reserved **expansion slot** and the rest for seeds. Among the seeds, framework text is capped at **2 chunks and 40% of the character budget** (exact integer arithmetic), and company policy is guaranteed **at least 2 seed slots**. The expansion slot is **released to the next company seed** when no linked chunk qualifies, so it is never wasted; unused framework quota goes to company seeds. Why a quota and not "company first, framework fills the rest": vector search always returns neighbours, so strict company-first would let irrelevant company text starve the one framework control a user named, while a hard quota keeps framework text from crowding out company policy in both directions. With the defaults: 2 company + 2 framework + 1 expanded chunk when a link exists, or 3 company + 2 framework when none does (both pinned by golden tests on the sample vault).

**Withdrawn controls** (`retrieval/withdrawn.py`). A framework chunk under the `Withdrawn controls` heading of a pack file (the converter's one-line stubs, ADR-008) is left out by default. The exception: a question that is **only identifiers** and names a control that has a stub in the chunk (`03.01.13`, `AC-3(1)`) gets that chunk back marked `withdrawn=True`. Known limit: stubs are grouped into chunks, so the chunk returned can hold other withdrawn controls' stubs too (all marked withdrawn, none carrying requirement text). A stub's *target* (`03.13.08`, which `03.01.13` says it is addressed by) is not a withdrawn ID and gets no exception.

**Graph expansion** (`retrieval/expansion.py`; CLAUDE.md 8.2). Edges are explicit links only, as the indexer resolved them, **outgoing only** (backlinks can flood the context with every document that cites a hub policy; they can be added later with their own cap). Only links with status `resolved` are followed (unresolved, ambiguous and rejected never are); `control_mappings` and similarity are never edges. A body link belongs to the chunk whose line range contains it; a frontmatter link belongs to every chunk of its document. At the target a `#Heading` fragment selects the chunks under that heading, otherwise the lead chunk (first by line) is used (known limit: it may not be the most relevant). Breadth-first, default depth 1, hard cap 2 (`expansion_depth` 0 turns it off), with a visited set seeded with the seeds so a cycle cannot add a chunk twice. Only the one expansion slot exists, so deeper expansion cannot grow the context. An expanded chunk is marked `role="expanded"` with `expanded_from` (the seed's chunk id), is not ranked (`fused_score` 0, no ranks), counts against the same character budget, never evicts a seed, and only company seeds expand (the packs have no links, and there are no cross-store edges).

**Identifier-first ordering (an addition to the merge, found by the golden tests).** For a question that is only identifiers, plain RRF order failed on the sample data for two measured reasons: an embedding blurs an identifier, so the nearest vectors of `03.01.01` are unrelated text, yet the one real keyword hit and the nearest vector tie at rank 1 under RRF and `chunk_id` decides; and BM25 prefers short chunks, so for `AC-2` the short enhancement chunks (`AC-2(4) ...`) outrank the control's own chunk. So (`retrieval/ordering.py`) for an identifiers-only question the candidates are tiered before the slots and the quota apply: (0) the chunk whose own last heading **is** the identifier (`AC-2 Account Management`, not `AC-2(4) ...` or `AC-20 ...`), (1) other keyword hits, (2) vector-only hits, with the RRF order inside each tier. Ordinary questions keep the RRF order. With it, every written form of the six controls in `retrieval_expectations.py` returns the same control first; without it, six golden tests fail (row 29).

## Known limits and hand-off to M5 (M4g)

What M4 does not do, stated once so M5 does not assume otherwise:

- **A non-empty result is not evidence.** There is no relevance floor and M4 sets no threshold. M5 decides "no evidence" itself (the verbatim-quote check, CLAUDE.md 8.4) and must refuse `framework_reference` chunks as evidence in code.
- **The offline tests prove mechanics, not semantic quality.** The golden tests use a hashed bag-of-words embedder, so they pin the keyword side, the merge, the quota, withdrawn handling, expansion and the flags. How well the real model ranks a paraphrase is measured only by the manual live check (`tests/test_retrieval_live.py`, `pytest -m ollama`), which prints the ranked results and shares its expectations (`tests/retrieval_expectations.py`) with the golden tests.
- **Rank-only fusion** ignores how strong a match was. **The expansion's lead chunk** may not be the most relevant chunk of the linked document. **Withdrawn stubs are grouped** into chunks. **The character budget is an approximation** (worst measured ratio, errs small). **`control_mappings` in frontmatter are not searchable** (frontmatter is not chunked); mapping is M5's job and needs the mappings stored (a schema change).
- **Packs are verified when loaded**, not on every question, and retrieval never refreshes or builds an index; one question runs at a time.
- **Identifier recognition** is whole whitespace-delimited words only, and a string such as `6.1` is also searched in its other written forms (harmless noise). The identifier-first ordering applies only to identifiers-only questions.
- M4 adds no HTTP route and no Tauri command: `Retriever` is an in-process interface until M5 has a caller, so the threat surface did not grow. Untrusted-data delimiters (CLAUDE.md 8.6) are applied when M5 builds a prompt; `RetrievedChunk.text` is documented as untrusted and returned byte for byte.

Mutation proofs in this ADR: M4d (1a, 1b, 10L, 28, N1), M4e (3a, 3b, 10a, 10b, 11, 12, 13, 14, 16, 17), M4f (2, 4, 5a, 5b, 6, 7, 8, 9, 18a, 18b, 23, 24, 29): 33 mutation proofs. The M4a and M4b proofs are in ADR-011 and ADR-009. The tie-break (rows 10a, 10b, 10L), the hollow greens (3, 5a, 7, 12, 13) and the limits above are recorded with the rows.

## Consequences

Positive: exact control IDs are findable even when an embedding blurs them, and a document that changes loses its lexical rows in the same transaction as its vectors. The tokenizer is built into SQLite (no package, no network).

Negative or risky:

- The table roughly doubles the text stored per chunk (the text is in `chunks` and in `fts_chunks`). The index is disposable, so this costs disk only.
- The quoting rule (item 3) is easy to forget. `tests/test_fts.py` pins the behaviour of the chosen tokenizer for every row of the table above, so a change to the tokenizer fails a test and has to update this ADR.
- Changing the tokenizer is a schema change: `SCHEMA_VERSION` is bumped and every index is rebuilt (ADR-009), which is cheap because the index is derived.

Revisit if a framework's identifiers use a character that the tokenizer splits in a way that breaks adjacency (none found so far), or if M4 finds the lexical side adds nothing the vectors do not already find.
