# ADR-005: Webview CSP, capabilities and the app command manifest

Status: Accepted. Evidence: round 1 (`pnpm tauri dev`) and mode B (debug build of the bundled app), both recorded below.

## Context

CLAUDE.md 3.2 says the webview's Content Security Policy is `default-src 'self'` with `connect-src` limited to `ipc:` and `http://ipc.localhost`, and Section 7 says capabilities grant only the specific commands each window needs. Three facts shape how that is configured and verified.

- Tauri's documentation says `csp` is injected into the HTML of the built application, and that `devCsp` is injected in development. It does not say whether that applies when the page is served by the Vite dev server. So this was measured, not assumed.
- **Round 1 evidence (2026-10-08, `pnpm tauri dev`, Tauri 2.12.1, `devCsp` set to a copy of the production string):** the window rendered; the console showed no Content Security Policy violation; `document.querySelector('meta[http-equiv="Content-Security-Policy"]')` was `undefined` (the served document is Vite's `index.html` with no CSP meta); `eval('1')` was allowed. With a policy that forbids `eval`, an allowed `eval` means no policy was in force. Conclusion: in `pnpm tauri dev` Tauri injects no CSP, so a `devCsp` has no effect and there were no violations to derive an allowance from.
- The first fetch probe, `fetch('http://127.0.0.1:1/')`, failed with `net::ERR_UNSAFE_PORT`. Port 1 is on Chromium's blocked-port list, so the request never reached CSP and the probe proved nothing. Every CSP probe uses a normal port, **65000**, and this applies to both modes and to the docs.
- Incidental observation from the same run: pressing Ctrl+Shift+I logged `webview.internal_toggle_devtools not allowed`. The capability no longer includes `core:default`, so that core permission is denied. This is not the proof that `sidecar_health` works under the trimmed capability (that is M2d).

## Decision

1. **One CSP, the shipped one.** `app.security.csp` in `tauri.conf.json` is `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, with `freezePrototype: true`. There is no `devCsp`: it would be a policy that is never applied. `data:` is not in `img-src` (nothing uses an image or data URI; adding one later needs a reason). `connect-src` contains only the IPC origins, so the webview cannot reach the sidecar's port even if it learned it. The host talks to the sidecar, never the window.
2. **The CSP is verified where it applies**: in a debug build of the bundled app (`pnpm tauri build --debug --no-bundle`, then `src-tauri\target\debug\desktop.exe`). A debug build keeps `debug_assertions`, so the dev sidecar path still resolves. The probes: `fetch('http://127.0.0.1:65000/')` must be refused by `connect-src`; `eval('1')` must throw; and the delivered CSP (meta string and response header, whichever exists) is recorded.
3. **One capability, one command.** `capabilities/main-window.json` applies to the window `main` and grants only `allow-sidecar-health`. `core:default` and `opener:default` are removed. `build.rs` registers the app manifest from `src/app_commands.rs` (the same file the crate compiles, so a test can pin the list), which makes the command permission-gated: without a manifest an app command is callable by every window with no permission. If a core permission turns out to be needed, it is added individually with the exact error text as evidence, never `core:default`. The devtools toggle is deliberately not granted.
4. **Tests pin the contents** (`tests/security_config.rs`): exactly one capability file; its exact keys, window and permissions; the command list; one window labelled `main`; every CSP directive and source; nothing remote, inline, dynamic or `data:`; `freezePrototype`; no `devCsp`; no `withGlobalTauri`; no plugin configuration. These tests read files; they do not prove the running app behaves that way.
5. The generated `permissions/autogenerated/sidecar_health.toml` is gitignored: `build.rs` regenerates it from `app_commands.rs` on every build (verified locally by moving it away and rebuilding, which produced an identical file).

## Consequences

- `pnpm tauri dev` has no CSP, so a CSP violation introduced by a frontend change will not show up in dev. It shows up in the bundled debug build and is checked there (manual check B in `docs/dev-setup.md`, M2d). CI does not render a webview.
- Frontend code must not need inline styles, inline scripts, `eval`, images from `data:` or any remote origin; the production CSP will block them.
- Adding a command is a security decision in three places that must agree: `commands.rs`, `app_commands.rs` and the capability file. The tests fail until all three do.
- The capability under `invoke()` is not proven here. M2d proves `sidecar_health` works with only `allow-sidecar-health`.

Revisit if: Tauri documents or changes CSP handling for dev-server pages; the frontend needs a remote origin or inline content; a second window or a plugin is added; or the sidecar is ever reached from the webview.

## Evidence: mode B (production `csp`, debug build of the bundled app)

Run by Mike on 2026-10-08 after a fresh `pnpm tauri build --debug --no-bundle`, starting `src-tauri\target\debug\desktop.exe`. The window was served from `tauri.localhost` (not the Vite dev server) and rendered the static page. DevTools opened with F12.

| Probe | Observed |
|---|---|
| `fetch('http://127.0.0.1:65000/')` | Refused by CSP, not by the port list: "Connecting to 'http://127.0.0.1:65000/' violates the following Content Security Policy directive: "connect-src ipc: http://ipc.localhost". The action has been blocked.", then `TypeError: Failed to fetch`. |
| `eval('1')` | `EvalError`: "Evaluating a string as JavaScript violates the following Content Security Policy directive because 'unsafe-eval' is not an allowed source of script: script-src 'self' 'sha256-HxZc9pz1bUHjVPSX7KvJxQJGzCnC+3tYUTJx3EpmrQs='." |
| CSP meta element | `undefined`: the policy is delivered as a response header, not a meta tag. |

What this shows and does not show:

- The configured `connect-src` and the absence of `unsafe-eval` are enforced in the bundled app. Round 1 allowed `eval` and this run blocks it, so the `eval` probe does tell an applied policy from none.
- Tauri appended a `'sha256-...'` source to `script-src`, as its documentation says it does for bundled code and assets. Which script the hash covers was not checked. The configured string has none, so the delivered policy is the configured one plus Tauri's hash. That sentence comes from the browser's error message; the response header text itself was not copied, so the full delivered policy is not recorded here.
- DevTools' own request to `http://tauri.localhost/.well-known/appspecific/com.chrome.devtools.json` was also blocked by `connect-src`. It is a DevTools request, not application code, and needs no allowance.
- The console again showed `webview.internal_toggle_devtools not allowed` (Ctrl+Shift+I); F12 opened DevTools anyway. The core permission stays ungranted.

Process observation, same run:

- While the app ran, `Get-Process` showed `desktop` (24140) and two `python` processes (4600, 35572), and no `fake_sidecar`. Two Python processes is what the venv launcher plus the real interpreter should look like (ADR-004), but their command lines and parent ids were not recorded, so this is consistent with that, not proof of it.
- After the window was closed, no `desktop` or `python` process remained.
- This shows the debug app started the dev sidecar and that the processes were gone after a normal close. It is NOT evidence that the sidecar reached `Ready` or answered `/health`: nothing in the window shows status yet. That is decided by `tests/real_sidecar.rs` (M2c commit 5) and by the live status in M2d.
